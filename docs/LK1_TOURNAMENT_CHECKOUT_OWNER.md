# LK1 tournament checkout through CUP admission

The LK1 tournament widget routes one-time, owned one-time and subscription-plus-tournament purchases to `POST /lk/tournament-checkouts`. The subscription visit and subscription money discount continue through `POST /lk/subscription-bookings`. CUP owns the rule in [ph-admin #131](https://github.com/Z6v6e6r/ph-admin/pull/131).

The new checkout accepts exercise ID, product source and ID, promo code and return URLs. It reads the authenticated Viva profile, verifies the exercise, and selects the product from Viva's exercise-scoped catalog or its owned one-time products. The existing Viva v2 WIDGET request retains the selected provider product, nested booking request, promo, studio and return URL aliases. Viva still calculates the charge. The browser no longer submits price or identity fields to the tournament write route. The custom energy and non-tournament paths retain their own routing.

Both server paths call `GET /api/tournaments/:exerciseId/level-decision` with the authenticated player. The gateway requires an enforced decision matching the verified Viva actor and exercise. It accepts the CUP rule version and stable outcomes, including `LEVEL_NOT_ALLOWED`, `PLAYER_LEVEL_REQUIRED`, `PLAYER_LEVEL_UNKNOWN`, `LEVEL_CHECK_UNAVAILABLE`, `ACTIVITY_LEVEL_INVALID` and `TOURNAMENT_RULE_CHANGED`. A missing link, response failure or actor/target mismatch fails closed. The gateway does not implement a level formula.

Subscription admission runs before new reservations and before reclaim or preaccept can acquire the daily-visit guard. Existing confirmed or in-flight provider outcomes retain their existing replay and recovery paths. The gateway uses the existing Viva category classifier for subscriptions.

Both paths share a key per Viva tenant, actor and exercise in the subscription operations Mongo collection. The graph builder requires the same Mongo client and collection on both paths. The runtime checks the exact production tenant, including on checkout. A separate ID prefix and nested bindings keep the shared rows outside ordinary subscription scans. The Mongo unique `_id` arbitrates the initial race, and a majority-acknowledged CAS fences every subsequent change by generation.

- Checkout claims `HELD` immediately before its Viva POST. It saves one exact provider transaction ID before replying. A replay of that selection can resume the existing transaction.
- Subscription claims `RESERVED` before writing its own attempt or taking the daily-visit guard. Only a majority-acknowledged transition to `HELD` within the reservation window and a matching local operation CAS permit the Viva POST. The Mongo server clock fences expiry and dispatch. Only an expired `RESERVED` can be replaced by elapsed time.
- `HELD` has no automatic expiry. Losing the request, the Mongo acknowledgement or the provider result keeps it held. A narrow provider refusal releases it only when the scoped subscription response was confirmed and the exact local attempt committed its failure with no booking or money evidence. Any managed entitlement must already be released. For cancellation, use the existing exact unpaid-money or returned-visit receipt. A seat-only release does not establish a financial or visit return.
- WIDGET checkout requires an exact cancelled sale, a terminal cancelled/expired card attempt, no payment/refund/issued-subscription effects, and a complete Viva read that confirms each linked booking is cancelled. An `UNPAID` sale with a rejected card can still accept a retry and stays held. A 4xx with no proven sale/booking outcome also stays held.
- A confirmed closure saves `RELEASED` and returns `409 TOURNAMENT_PREVIOUS_ATTEMPT_CLOSED`. The widget clears its stale payment selection. A separate later click passes fresh CUP admission and acquires the next generation. The losing acquisition emits no provider POST.

The graph builder reads a fresh verified 147 snapshot from outside Git. It pins the full source and subscription function hashes, changes the subscription router's `func` only, and adds a separate checkout graph. Check the graph contract and the matching nginx location before any rollout. The node requires the existing server Viva tenant in `VIVA_TENANT_KEY`. Its CUP decision origin is the production CUP API. Isolated tests should stub both upstreams. Do not import a production candidate into the isolated runtime.

## Release gaps

- Viva v2 receives the same authorization and uses the same pricing endpoint. Moving the call behind LK1 changes its route, but cannot change what a previously issued client credential may do at Viva. A provider restriction must reject the ordinary client and permit the server's equivalent purchase for the same exercise. Widget visibility, read-only exercise metadata and available catalogs cannot establish that restriction.
- Sampling 18, 19 and 21 November identified 40 registering Viva tournaments mapped to CUP and classified as tournaments. Confirm every rollout exercise, including custom types and directions. A CUP-linked event misclassified upstream can still miss the subscription gate.
- Before rollout, inventory legacy `PREPARED` and unresolved attempts created before the common key was introduced. They can already own a daily guard or provider-side outcome. Reconcile those against their original owner evidence before switching.
- If a process stops or the short `RESERVED` interval elapses after a local daily or managed-entitlement reservation, the old request can no longer send a Viva POST. A definitely failed shared dispatch CAS can fail the exact unstarted unmanaged operation. Uncertain outcomes and outstanding managed reserves may still require reconciliation through the existing owner. An in-flight payment or visit may never be guessed from time.
- Unknown WIDGET attempts without an exact provider transaction and linked booking remain held. Prove the authoritative terminal DTOs and pricing parity on the isolated Viva exercise. Do not assume an observed terminal DTO shape on production from synthetic fixtures.
- No live provider write, payment, migration, Node-RED import, frontend publication or deployment was performed. This candidate does not establish P0 closure.
