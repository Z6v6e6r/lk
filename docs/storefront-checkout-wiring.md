## Что подключено

`src/components/storefront-checkout/StorefrontJoinCheckout.tsx` заменяет только ветку split-оплаты в `details-join-action-row` и только при включённом флаге.

| Действие витрины | Вызов на `main` |
|---|---|
| «Перейти к оплате · X ₽» (разовое участие) | `handleSplitJoinCurrentUserFromDetails("one_time")` → `apiCreatePadelSplitParticipantPayment` → страница банка |
| Выбор подписки | `handleSplitJoinCurrentUserFromDetails("subscription", id)`; выбор доступен только при котировке `available` |
| «Перейти к оплате» в ожидании | `paymentUrl` из `PAYMENT_PENDING` записи игры |
| «Покинуть игру» | `handleLeaveCurrentUserFromDetails` |
| «Проверить статус оплаты» | новое `recheckSplitJoinOutcome`: перечитывание игры (`no-store`); блок снимается только по доказательству |

Состояния выводятся только из записи игры: «выбор», «ожидаем оплату» (с серверным сроком), «только выход». Успех — это появление игрока в составе после подтверждения сервером; сам блок успеха не показывает.

## Изменения поведения

1. **Двойная отправка.** Несколько кликов в одной задаче доходили до обработчика 3 раза, по 3 разных `paymentRef`. Блок витрины держит синхронную защиту до следующей задачи. На синтетическом сервере 3 клика дают 1 команду.
2. **Неизвестный исход разовой оплаты (H090).** Исходная попытка хранится в существующем журнале `SplitCreateAttempts`: отдельный экземпляр в `apiClient`, ключ `lk_split_join_attempt_refs_v1:game:<gameId>`, значение — только `paymentRef`.
   - **Порядок под блокировкой.** Проверка, запись в журнал и POST выполняются под эксклюзивной Web Lock на игру. Если Web Locks недоступны, разовая оплата не отправляется (`SPLIT_JOIN_ATTEMPT_LOCK_UNAVAILABLE`, блок по умолчанию).
   - **Запись должна быть надёжной.** После `begin()` запись перечитывается из хранилища. Если она не подтвердилась (квота, ошибка хранилища) или другое окно успело записать свою попытку, POST не отправляется (`SPLIT_JOIN_ATTEMPT_JOURNAL` / `SPLIT_JOIN_ATTEMPT_UNRESOLVED`).
   - **Пока попытка удержана**, новый create с новым `paymentRef` не отправляется ни из одного UI (флаг ON/OFF, `GameJoinPage`).
   - **Чем снимается.** Только доказательством по **этому** `paymentRef` из свежей записи игры:
     - `PAID` — успех;
     - точный подтверждённый провайдером отказ (`CANCELLED`/`CANCELED`/`DECLINED`/`FAILED`/`REJECTED`/`VOIDED`/`VOID`) разрешает новую осознанную попытку.

     Промежуточные (`CANCELLING`, `CANCEL_REQUESTED`, `PENDING_CANCEL`, `VOID_PENDING`), дедлайновые (`EXPIRED`, `RELEASED`, `CANCELLED_EXPIRED`), `ERROR`, `REFUND*` и `PAYMENT_PENDING` удерживают попытку: дедлайн сервера — тоже таймер, а поздний `PAID` возможен.
   - **Снятие только под блокировкой.** Любое снятие удержания (повторное чтение, загруженная запись игры) идёт под той же Web Lock и заново проверяет, что удержан тот же `paymentRef`. Без Web Locks удержание не снимается.
   - **Ответы сервера.** Удержание снимается только при отказе до провайдера: 400, 401, 403, 404 или 422 без кода `SPLIT_JOIN_CHECKOUT_PENDING`. 409 (в пилоте он приходит после шагов провайдера), 423, 429, 408, 5xx и сетевой сбой удерживают. Снятие — сравнение-и-удаление: запись удаляется, только если в ней всё ещё этот `paymentRef`.
   - Таймер блок не снимает. Записи других попыток этого же игрока, включая старые `CANCELLED`, доказательством не считаются.
   - **Ограничения.** Журнал живёт в браузере: другое устройство или очищенное хранилище его не видят. Отсутствие элемента с этим `paymentRef` (например, POST не дошёл до сервера) блокирует новую оплату для этой игры без пути выхода для пользователя: нужен серверный путь сверки. Серверный идемпотентный ключ разовой оплаты — отдельный follow-up, поэтому повторные платежи этим изменением **не исключены**.
3. **Неизвестная цена.** Разовое участие без серверной цены нельзя выбрать. Старый обработчик в этом случае подставлял 2 500 или 5 000 ₽; через витрину этот путь недостижим.

## Не входит в этот срез

Тренировка, турнир, создание игры, MX, резидентство, подписка и Буст как покупки, составной заказ (#441/#443). В подключённом режиме предложения покупки продуктов на экране игры не показываются. Остальные экраны стенда по-прежнему на локальной имитации — см. приёмку `acceptance/lk1-storefront-02000ad7/`.

## Независимая проверка (CRITICAL, путь оплаты)

Раунд 1 на `46ce14cc` нашёл два блокера: сеть и 5xx не удерживали попытку, пустое чтение снимало блок. Они исправлены в `7a32f4ca`. Координатор затем указал, что блок по-прежнему снимался таймером, любой старой записью игрока и терялся при перезагрузке. В этой версии всё это заменено журналом исходной попытки. Результат повторной независимой проверки — в описании PR.

Follow-up finding: создание разовой оплаты не идемпотентно на сервере между попытками (`operationId = paymentRef`), кроме пилота `LK_PAID_SPLIT_JOIN_RECOVERY`. Нужен серверный ключ; это отдельная работа уровня CRITICAL.
