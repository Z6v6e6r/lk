# Уровень игрока только в ЦУП

## Продуктовый контракт

Новый игрок не имеет уровня. Первое назначение возможно только через онбординг самого
игрока либо сотрудником с правом `player-ratings:write` в ЦУП. Отсутствие записи не
означает D/1.0. Сбой чтения, конфликт идентичности и история без проекции не означают
отсутствие уровня. Первое назначение никогда не перезаписывает существующую историю.

Канонические данные: `rating_events` + `player_rating_state`; `player_ratings` остаётся
совместимой проекцией ЦУП. Снимки в играх и сообществах не являются источником нового
уровня. Рабочая шкала ЦУП/ЛК сохранена: D <2, D+ <3, C <3.5, C+ <4, B <4.7,
B+ <5.5, A до 7. Числовые значения при выравнивании букв не меняются.

Существующая анкета онбординга и её расчёт сохранены. Перед ней добавлен выбор:
указать известный числовой уровень 1–7 либо определить его по анкете. Оба пути используют
тот же initial-only endpoint ЦУП. Экран успеха появляется только после канонического
подтверждения сохранения.

При новой записи в ЛК на тренировку, игру или турнир с явным ограничением уровня
проверяется свежий уровень ЦУП. Для `UNRATED` предлагается тот же онбординг поверх
выбранного события; после сохранения клиент возвращается к записи и подтверждает её сам.
`UNAVAILABLE` требует повторной проверки, а не первого назначения. Без ограничения
онбординг не требуется. Продолжение уже созданной оплаты и выход из игры не блокируются.
Диапазон формулы пересчёта `params.minRating/maxRating` не является правилом допуска.
В основной информации события и в окне перед онбордингом показывается допустимый
уровень из настроек события. Точные буквенные деления сохраняются; раздельный список
допуска не превращается в непрерывный диапазон. При отсутствии данных уровень не выдумывается.

Это проверка сценариев интерфейса ЛК. Разовая оплата по-прежнему может идти напрямую
в Viva, поэтому универсальный серверный запрет обхода через прямой запрос к провайдеру
этим изменением не обеспечивается. Для него нужен отдельный gateway/provider contract.

## Реализация и совместимость

- `GET /lk/games/ratings/me`: Bearer проверяется через профиль Viva исключительно для
  идентификации. Ответ ЦУП содержит `RATED` либо `UNRATED`, числовой уровень, букву и
  непрозрачную версию. Контакты и внутренние ключи событий не возвращаются.
- `POST /lk/games/ratings/live`: теперь авторизованный пакетный канонический read по
  точным clientId/записанным aliases, максимум 100 ID; phone/name/caller-rating fallback
  удалён. Клиенты без ID показываются без уровня до разрешения идентичности.
- `POST /lk/onboarding/level`: actor берётся из проверенного профиля, чужой clientId
  запрещён. Транзакция создаёт `RATING_INITIAL_ASSIGNED`, state и compatibility вместе;
  та же анкета повторяется идемпотентно, другая не заменяет имеющийся уровень.
- Новый private child `/opt/padlhub-player-level/current/level.mjs` собирается
  `node scripts/build_cup_player_level.mjs NEW-ABSOLUTE-DIRECTORY` только из clean source.
  Зависимость mongodb берётся из существующего rating-worker runtime. Mongo URI не
  передаётся в argv/stdout. Проверки уникальных индексов ничего не создают.
- Онбординг сериализуется общим data flock с worker. DB-транзакция и уникальные индексы
  защищают от гонки с первым назначением через ЦУП. Phone-only история/ownership требует
  восстановления; автоматического слияния по имени/телефону нет.
- Уровни карточек игр, профиля, списка/состава сообщества и текущая колонка уровня рейтинга
  сообщества обновляются из ЦУП. Очки рейтинга и исторические результаты не изменяются.
  Snapshot adapter перед вступлением/управлением/автодобавлением обновляет поддерживаемые
  member/creator/actor/owner/user/manager/target/participant aliases; исходные обработчики
  прав остаются downstream. HTTP Bearer проверяется до чтения Mongo, включая phone-only
  и пустые наборы целей. Неопределённый уровень не превращается в C/3.2.
- ФПР допускает только существующие уровни ЦУП; bootstrap из Viva и default1 отключены.
  Новый игрок сначала проходит анкету/назначение. Исторические FPR-расчёты могут
  восстанавливать проекцию из ранее назначенного baseline, но не назначают первый уровень.
- Viva dispatch обоих workers отключён. Legacy V1 retry не выбирает очередь; текущий
  confirm получает явный `NOT_REQUIRED`, без фиктивного SUCCESS синхронизации. Исторические
  очереди сохраняются. Старые генераторы/repair Viva завершаются явной ошибкой retirement.
- Физическая идентификация, контакты, авторизация, бронирования и оплаты продолжают
  использовать Viva. Ни один рабочий процесс уровня не читает и не пишет её level fields.
- Изменение в ph-admin связано с этим переходом. CUP→LK2 projection сохраняется;
  `RATING_INITIAL_ASSIGNED` адаптируется к существующему wire event type без изменения
  контракта получателя. Никакие live-права тренерам автоматически не выдаются.

## Проверяемый кандидат Node-RED

Снимать свежий `/root/.node-red/flows.json` с 147 только чтением в новый private каталог
вне Git (каталог 0700, файлы 0600). Raw flow содержит чувствительную конфигурацию и не
должен попадать в PR, артефакты CI или сообщения.

```
node scripts/patch_cup_only_player_level.mjs \
  /private/path/source.flow.json EXACT-SOURCE-SHA256 \
  /private/path/NEW-candidate.flow.json /private/path/NEW-report.json
```

Генератор работает offline, проверяет SHA полного source, обязательные узлы, endpoint
preimages, уникальные ID, конечные связи и отсутствие необработанных Viva level field IDs.
Сохранены все остальные узлы; общие community helpers нормализуются в каждой встроенной
копии. Проверка кандидата не означает import/deploy. При дрейфе target сначала повторяется
чтение и review нового diff; старый snapshot не используется как разрешение на выпуск.

Текущий modular `validate` проверяет точную read-only extraction исходной вкладки, а не
изменённый release graph; его нельзя выдавать за проверку этого кандидата. Применяются
full-graph fingerprint/links/function compile и отдельный изолированный runtime rehearsal.
Никогда не запускать полный боевой graph локально: inject/startup hooks могут писать.

## Условия живого перехода — отдельная операция

1. Зафиксировать clean pushed commits обоих PR, CI, Node-RED disk/runtime/editor revision
   и worker manifests. Сохранить защищённые backup flow, state, событий, индексов и Viva
   level fields; проверить восстановление копии вне production.
2. Выполнить read-only aggregate audit:
   `node --experimental-strip-types scripts/audit_cup_player_level_cutover.mjs` с заранее
   настроенным read-only `MONGODB_URI`. Он ничего не создаёт/меняет и выводит только counts.
   Его `canonicalCoverageReady` не заменяет полный инвентарь Viva: последний явно помечен
   `fullVivaClientInventoryVerified: false`.
3. Сверить точные clientId/aliases всех существующих уровней Viva, ЦУП и старой compatibility
   проекции. Существующий канонический уровень ЦУП не перезаписывать значением Viva.
   Missing canonical, orphan history, alias conflicts, несогласованные буквы и отсутствующие
   уникальные индексы разбираются отдельным dry-run/планом с точным списком записей.
   Реальный import/backfill/изменение индексов этим PR не выполняется и требует разрешения.
4. Согласовать и остановить старые отправители уровня; дождаться завершения `SENDING`.
   Legacy очереди оставить для аудита, не replay/delete. Сначала установить проверенные
   child/worker/helper artifacts, затем согласованно активировать backend graph, ЦУП и ЛК.
   FPR helper и workers пересобираются вместе: их hash guards нельзя обходить.
5. Проверить под реальными авторизованными ролями: existing/unrated/error; первая анкета,
   её retry и запрет overwrite; назначение сотрудником и запрет без права; карточки игр,
   состав/управление сообществом; ФПР и обычный результат; сохранённая проекция ЛК2.
   Уровневые операции не должны обращаться к Viva custom fields. Нужны отдельные mobile
   и desktop UI проверки через подтверждённый маршрут браузера.
6. Физически удалять level fields Viva только после полной проверки отсутствия внешних
   потребителей и отдельного разрешения на точные поля. Для cutover достаточно прекратить
   их использование. Не удалять исторические rating_events или provider queues.

После первого нового canonical-only назначения старый frontend/flow с чтением Viva не
является безопасным rollback: в Viva уже нет новых уровней. Предпочтительно forward-fix;
обратный переход требует отдельной сверки и согласованного восстановления проекций.
Этот документ и подготовленный кандидат не разрешают merge, deploy, restart, live data
mutation, изменение прав или удаление полей.

## Совместный кандидат с турнирным владельцем

Патч канонического уровня выполняется первым, затем к его полному выходному графу
применяется `prepare_tournament_admission_candidate.mjs` с SHA-256 промежуточного файла.
Генератор сохраняет маршруты, инъекты, текущие политики абонементов и отдельный маршрут
Pade Prime. Снимок Pade Prime имеет собственный префикс и сохранённые правила. Этот
кандидат переключает PadlHub. Любая дополнительная ссылка на поля уровня Viva в
основном контуре прерывает сборку.

Read-only аудит принимает приватный 0600 JSON-экспорт Viva с `tenantKey`, `complete`
и массивом `clients`. Каждая строка содержит `tenantKey`, точные `clientId`, `ratingNumeric`
и `rating`. Для игрока без уровня оба последних значения равны null.
`CUP_LEVEL_AUDIT_TENANT` фиксирует согласованный tenant. Параметр
`--viva-inventory /absolute/private/export.json` добавляет dry-run сравнения без публикации
ID, применения правок или утверждения полноты выгрузки. Сверять покрытие и источник
экспорта нужно отдельно. Записи Viva не изменяют значения ЦУП.

На переходе остановить доставку уровня в Viva из `rating_worker`, `game_result_rating_worker`
и legacy retry flow. Дождаться разрешения всех `SENDING`, сохранить очереди на месте.
ЛК2 принимает проекцию через отдельный outbox. Обновление приёмника и миграция его
проекции должны быть готовы до проверки отправителя вычисленных событий.

### Корректировки уровня из ЦУП

События `RATING_MANUALLY_CHANGED` с `source.kind=ADMIN_MANUAL` задают абсолютное
`change.after`, в том числе после накопления дельт за границей шкалы. Старые записи
сохраняют исходную семантику. Позднейшие игровые события применяются поверх заданного
значения. Новые расчёты сохраняют ссылку на точную версию результата или протокола.

Для этого изменения используется полный пакет rating worker. Исторические частичные
FPR-пакеты оставляют компоненты проигрывания разных версий и не подходят для выпуска
или отката после появления нового ручного события. Перед переключением согласовать
встроенные узлы результатов, закрыть ожидающие задачи старого игрового пути V1 и
проверить уже подготовленные игровые планы. Новые расчёты игры и их проекции фиксируются
в одной MongoDB-транзакции. Для обычного турнира каждая запись игрока проверяет версию
канонического состояния, от которой строился план, и повторно рассчитывается после
конфликта в следующем проходе.
