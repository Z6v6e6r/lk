# Подтверждение разовой групповой записи со скидкой

Стадия: локальное исправление, не опубликовано и не развёрнуто.
База: `origin/main` = `ba2588af1492c76fa44dbcd75246762dcefcc309`.
Ветка: `codex/group-booking-confirmation-20260910`.

## Причина по HAR и установленному обработчику

OPTIONS уже отвечает 204. Первый POST записи возвращает 202 с
`LK1_BOOKING_OUTCOME_UNKNOWN`, последующие запросы — `LK1_BOOKING_OUTCOME_UNRESOLVED`.
Установленный обработчик выдаёт первый код после успешного ответа Viva без устойчивого
bookingId. Он останавливается до создания транзакции. Сам ответ серверного Viva POST
в браузерном HAR отсутствует; его точная форма не доказана.

Дополнительно собственный список Viva содержит запись с `id` и `exercise.id`, но не
содержит повторения `clientId`. Строгая прежняя проверка владельца отклоняет такой DTO
даже при известном точном bookingId. HAR сохранён вне Git; в тестах только синтетические
идентификаторы, без заголовков авторизации и персональных данных из HAR.

## Изменение

- Только HTTP `BOOK_GROUP_TRAINING`, категория `group_training`, денежная льгота
  `PERCENT_DISCOUNT`, ноль посещений и `ON_PLACE` используют Admin v1 POST
  `/api/v1/exercises/{exerciseId}/bookings`. Этот маршрут уже используется split-контуром.
  Другие HTTP-сценарии сохраняют v2, split сохраняет v1. Политика размера скидки не меняется.
- Обязателен устойчивый ID из ответа создания. Подбор записи по упражнению/времени
  и повторное создание при неопределённом исходе не добавлены.
- Для точного bookingId отсутствие owner-полей допустимо только после серверного GET
  `/end-user/api/v2/{tenant}/bookings?size=1000` с пользовательской авторизацией.
  Одноразовый маркер связывает запрос с actor, operationId/key, URL и текущим токеном;
  проверяются GET, URL ответа и запрет redirects. Маркер удаляется при обработке ответа,
  не записывается в Mongo, ошибки или логи. Заголовки HTTP-ответа не используются как
  доказательство исходной авторизации: Node-RED заменяет ими заголовки запроса.
- Явно неверные/конфликтующие owner-поля, отмена, другой exercise, другой тип оплаты,
  подписочное списание, дубли и существующая платёжная информация блокируют подтверждение.
  Непустой `transactionStatus` блокируется консервативно, даже при будущей безобидной форме DTO.
- Исходная защита durable acknowledgement и transaction CAS сохранена.

`scripts/patch_nodered_group_booking_confirmation.mjs`.

## Ограничения и следующий этап

Live-синхронный ответ Admin v1 для групповой записи, подбор платёжного продукта и
получение ссылки на оплату ещё не проверены. Локальная VM подтверждает переход к
checkout после точного ID и durable ack, но не заменяет провайдерный smoke.

Уже зависшие операции остаются заблокированными. Автоматической перепривязки или
изменений Viva/Mongo нет; их восстановление требует отдельной авторитетной сверки.

Перед одобренным развёртыванием обязательны свежая выгрузка 147, проверка preimage,
проверенный commit/CI, штатный exact-graph deploy с backup/lease и postcheck. При drift
нельзя накатывать этот сохранённый поток или перегенерировать его широкой цепочкой.
