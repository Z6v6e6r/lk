# Четыре кампании реактивации Telegram

Подготовка на срезе **30 сентября 2026 года**, подтверждённом владельцем.
Модуль добавляет отдельную отключённую вкладку Node-RED, журнал по получателям
и четыре кнопки запуска. Существующий бот и его flow не переписываются.
Импорт, создание Mongo-коллекций и индексов и отправка здесь не выполнялись.

## Конфигурация сообщений

Скопировать `scripts/telegram_reactivation/campaigns.example.json` в отдельный
приватный файл 0600 вне Git. Внести реальный `botId` из `getMe`, четыре
`fileId` и точные тексты/подписи, полученные через того же бота.
Типы: `photo`, `video`, `message`. Лимит подписи 1 024 символа,
текста 4 096. Отправка идёт обычным текстом без HTML/Markdown-разметки.

Ссылки в примере переписаны со скриншотов и должны быть сверены с финальными
текстами. Предложенные `utm.campaign` — ключи для настройки, а не доказательство
текущих меток коротких ссылок. Проверить конечный URL каждой короткой ссылки,
записать фактические source/medium/campaign и только затем поставить
`utmConfirmed: true`. В каждой кампании нужен свой уникальный utm.campaign.
Полный URL с UTM сверяется автоматически. Сам текст должен содержать `link`.
Модуль не добавляет и не меняет метки молча.

Генерация отключённого импорта из исходного JS:

```bash
node scripts/telegram_reactivation/build_flow.mjs /absolute/new-reactivation.flow.json
```

Все ID уникальны, связи внутренние, credentials/получателей/старых узлов в
импорте нет. Новые HTTP endpoints не создаются.

## Предпосылки перед разрешённым подключением

Node-RED с `functionExternalModules: true`, Node.js 20+ и **mongodb driver 6+**.
Function импортирует `mongodb`, встроенные `https`, `crypto`, `fs`.
Старый `node-red-node-mongodb` не обеспечивает подтверждения записи и здесь
не используется. Проверить установленную версию driver и подключение на целевом
сервере до активации. URI/токен задаются окружением и не переносятся из присланного
экспорта. Mongo должен поддерживать подтверждённые записи `w: majority`.

Переменные окружения:

| Имя | Значение |
| --- | --- |
| TG_REACTIVATION_MANIFEST | Абсолютный путь к приватному recipients.private.json |
| TG_REACTIVATION_CONFIG | Абсолютный путь к приватной конфигурации сообщений |
| TG_REACTIVATION_MONGO_URI | URI согласованной MongoDB |
| TG_REACTIVATION_MONGO_DB | Согласованная база MongoDB |
| TG_REACTIVATION_BOT_TOKEN | Токен именно выбранного бота |
| TG_REACTIVATION_SEND_ENABLED | `true` только при разрешённом запуске |

PREVIEW читает и валидирует файлы, не подключается к Mongo и ничего не отправляет.
PREPARE создаёт `tg_reactivation_batches`, `tg_reactivation_recipients` и два
индекса, фиксирует хэши аудитории/сообщений и подтверждает полную загрузку.
Это запись в согласованную базу, выполняется только после разрешения на подключение.
Повтор PREPARE не сбрасывает результаты. Нельзя менять сообщения/аудиторию/бота
под прежним batchId после подготовки.

RUN отправляет до 25 адресатам выбранной кампании (по умолчанию academy),
START academy/friendship/group/return проходит выбранный сегмент полностью,
публикуя агрегаты после каждых 25 адресатов. Ручной запуск, без inject-once,
cron или автозапуска при импорте/перезапуске. Одновременно работает один
отправитель этого бота. Отключить параллельные старые рассылки: они не участвуют
в новом ограничителе. Скорость до одного запроса в 1,1 секунды; для всей базы
минимум около 3,7 часа плюс ответы Telegram/Mongo.

При 429 сохраняется retry_after, проход останавливается, повтор до трёх попыток
возможен после указанного срока. Ошибка текста/медиа/авторизации и неопределённый
результат останавливают проход. Не редактировать конфигурацию уже начатой кампании.

## Что измеряется

Отчёт REPORT и выход Function возвращают только агрегаты для четырёх кампаний:
eligible, attemptedRecipients, attempts, accepted, blocked, unreachable, failed,
pending, sending, retry_wait, unknown, suppressed_blocked, acceptanceRate, UTM.
Счётчики рассчитываются по сохранённым состояниям, не увеличиваются повторными
callback/нажатием кнопки. `attempts` — число начатых попыток API, в том числе повторов;
`attemptedRecipients` — уникальные адресаты с начатой попыткой.

- **accepted / отправлено**: Telegram вернул Message с message_id и нужным chat.id.
  Это подтверждение приёма сообщения Telegram, доставка/прочтение не измеряются.
- **blocked**: только 403 с точным `bot was blocked by the user`.
- **unreachable**: удалённый аккаунт, chat not found или запрет инициировать диалог.
- **unknown**: timeout, неопределённый ответ или незавершённая попытка после сбоя.
  Такие адресаты автоматически повторно не отправляются.
- **suppressed_blocked**: блокировка ранее подтверждена этим модулем для того же бота.
  Существующие исторические блокировки пока не импортируются. Разблокировка
  потребует отдельного подтверждённого входящего события и согласованной доработки.

API использует только api.telegram.org, ограничивает время/размер ответа.
В debug нет chatId, payload Telegram, токенов, URI и сырых ошибок.
В базе есть адреса доставки, поэтому доступ к коллекциям должен быть ограничен.
Поадресный журнал можно выгрузить приватно отдельно, агрегаты нельзя использовать
как доказательство индивидуальной покупки.

## Сбой и восстановление

Перед API подтверждается атомарное состояние `sending`. Если Telegram ответил,
но запись результата не подтверждена, блокировка бота сохраняется. TTL и
автоматического перехвата блокировки нет. При повторном запуске отправка запрещена.

Восстановление разрешается после остановки прежнего процесса/отправителя,
а не просто по истечении времени. Через отдельный ручной inject передать
`action: recover`, `owner` из REPORT.lock и `workerStopped: true`.
Все `sending` этого владельца переводятся в `unknown`, затем снимается блокировка.
Нельзя возвращать `unknown` в `pending`: Telegram не предоставляет идемпотентного
ключа для sendPhoto/sendVideo/sendMessage. При неопределённости возможен пропуск,
поэтому требуется приватная сверка, а не автоматический повтор.

Откат модуля: остановить отправитель, отключить вкладку, сохранить журнал.
Отправленные сообщения и уже созданные данные этим откатом не отменяются.
Не включать старый send-all inject как восстановление новой кампании.

## Покупки — следующее подключение

`purchased`, `revenueRub`, `purchaseConversion` пока **null**, не ноль.
Нужно событие подтверждённой оплаченной покупки: уникальный purchaseId,
paidAt, фактическая сумма, campaignId/utm.campaign и доказательство атрибуции.
Покупки дедуплицировать по purchaseId; считать оплаченные, отдельно учитывать
возвраты и различать количество покупок и уникальных покупателей.
Общие UTM дают атрибуцию кампании, но сами по себе не связывают покупку с chatId.
Для индивидуальной воронки нужен доверенный переход/идентификатор пользователя;
телефон, имя или похожий email не являются основанием для объединения личностей.
Промокод без меток сам по себе не доказывает источник покупки.
