# Четыре кампании реактивации Telegram

Подготовка на срезе **30 сентября 2026 года**, подтверждённом владельцем.
Модуль добавляет отдельную отключённую вкладку Node-RED, журнал по получателям
и четыре кнопки запуска. Существующий бот и его flow не переписываются.
Импорт, создание Mongo-коллекций и индексов и отправка здесь не выполнялись.

## Конфигурация сообщений

Скопировать `scripts/telegram_reactivation/campaigns.example.json` в отдельный
приватный файл 0600 вне Git. Внести реальный `botId` из `getMe`, четыре
`fileId` и точные тексты/подписи, полученные через того же бота.
Типы: `photo`, `video`, `message`. Лимит подписи 1 024 символа,
текста 4 096. Отправка идёт обычным текстом без HTML/Markdown-разметки.

Ссылки в примере переписаны со скриншотов и должны быть сверены с финальными
текстами. Предложенные `utm.campaign` — ключи для настройки, а не доказательство
текущих меток коротких ссылок. Проверить конечный URL каждой короткой ссылки,
записать фактические source/medium/campaign и только затем поставить
`utmConfirmed: true`. В каждой кампании нужен свой уникальный utm.campaign.
Полный URL с UTM сверяется автоматически. Сам текст должен содержать `link`.
Модуль не добавляет и не меняет метки молча.

Генерация отключённого импорта из исходного JS:

```bash
node scripts/telegram_reactivation/build_flow.mjs /absolute/new-reactivation.flow.json
```

Все ID уникальны, связи внутренние, credentials/получателей/старых узлов в
импорте нет. Новые HTTP endpoints не создаются.

## Предпосылки перед разрешённым подключением

Node-RED с `functionExternalModules: true`, Node.js 20+ и **mongodb driver 6+**.
Function импортирует `mongodb`, встроенные `https`, `crypto`, `fs`.
Старый `node-red-node-mongodb` не обеспечивает подтверждения записи и здесь
не используется. Проверить установленную версию driver и подключение на целевом
сервере до активации. URI/токен задаются окружением и не переносятся из присланного
экспорта. Mongo должен поддерживать подтверждённые записи `w: majority`.

### Облачный импорт без файлов на сервере

`build_cloud_flow.mjs` создаёт отдельный отключённый импорт с фиксированными
chatId и готовыми четырьмя постами внутри Function. Этот JSON содержит приватную
аудиторию и не должен попадать в Git/PR или публичные ссылки.

```bash
node scripts/telegram_reactivation/build_cloud_flow.mjs \
  /absolute/private-manifest.json /absolute/private-posts.json /absolute/new-cloud.flow.json
```

Для изменённой аудитории нужен новый batchId до первого запуска. После PREPARE
и начала кампании не менять batchId, адресатов, бота или посты. Повторные START
под тем же batchId продолжают pending, а не создают повторную рассылку.

Облачная версия использует реальные подтверждения native MongoDB driver,
включая уже установленный вместе с MongoDB-узлами driver **3.7.4** и современные
версии. `mongo_compat.mjs` нормализует подтверждение результата и разворачивает
атомарный claim; legacy `mongodb out` не заменяет acknowledgement.
Клиент принудительно задаёт `w: majority`, `j: true`, primary и majority reads.
Проверка старого driver выполнена offline на его реальных классах операций.
Topology, установленные библиотеки и настройки целевого облака требуют проверки.

Function требует разрешённых модулей `mongodb`, `https`, `crypto`; fs не используется.
Если корневой `mongodb` повреждён, не обновлять его вслепую: он общий для других
узлов. После отдельно разрешённой установки официального npm alias
`tg-reactivation-mongodb@npm:mongodb@3.7.4` в shared userDir Function должен
ссылаться на **bare** `tg-reactivation-mongodb`, import as `mongo`. Полный npm spec
при загрузке Function не является именем модуля. Установка alias всё равно может
пересобрать общие npm зависимости. Генератор принимает bare alias четвёртым
аргументом CLI после пути output. Не повторять npm install при ошибке загрузки
уже зарегистрированного alias; проверить результат установки и остановить этот путь.
Async Function завершается средствами Node-RED после выполнения promise;
глобальная функция `done` в редакторе не предоставляется.
Четыре переменные окружения процесса/секретных настроек хостинга:
`TG_REACTIVATION_MONGO_URI`, `TG_REACTIVATION_MONGO_DB`,
`TG_REACTIVATION_BOT_TOKEN`, `TG_REACTIVATION_SEND_ENABLED`.
Сначала SEND_ENABLED=false; PREVIEW не подключается к Mongo/Telegram,
PREPARE создаёт журнал, после проверки PREPARE и конфигурации включается отправка.
Не записывать токен/URI в Function, flow JSON или переписку.
В Node-RED 4.0.9 можно использовать environment properties самой вкладки:
URI и BOT_TOKEN имеют тип `cred`, DB и SEND_ENABLED — тип `str`.
Штатный редактор переносит значения `cred` в отдельный encrypted credential store
и удаляет их из `env.value`; проверить, что шифрование credentials не отключено.
SEND_ENABLED должен содержать строку `false`/`true`: boolean не проходит строгую
проверку wrapper. Настройки вкладки позволяют узкий deploy; глобальные env
меняют global-config и требуют полного deploy.
По адресу редактора без авторизованной сессии доступны только поля входа;
права на модули и процессные переменные этим не подтверждаются.

Для явно разрешённого переноса существующих Mongo/Telegram credentials между
config nodes и новой вкладкой доступен одноразовый административный CLI
`scripts/telegram_reactivation/configure_cloud.mjs`. Он работает на самом сервере,
читает только указанные config IDs из decrypted in-memory store и использует
существующую действующую сессию указанного оператора из `.sessions.json`.
Чтение этих приватных хранилищ и сохранение credentials требуют отдельного
разрешения на точный источник и получателя. CLI не является библиотекой Function.
Он не создаёт токены, ключи, пароли или plaintext-файлы с секретами, не пишет секреты в stdout.

Plan JSON содержит только userDir, port, adminRoot, username, flowId, controllerId,
controllerHash (SHA-256 JSON из func, initialize, finalize, libs), mongoId,
mongoHash (SHA-256 JSON из hostname, port, db, connectOptions, topology),
botConfigId, botId и database. Секретные поля и
внешний API host запрещены. `node configure_cloud.mjs /absolute/plan.json --check`
проверяет конфигурацию без записи; `--apply` передаёт только credentials новой
вкладки в loopback API. GET/POST `/flows` использует v2 revision CAS и deployment
type `nodes`; остальные узлы сохраняются точно. При конфликте нет автоматического
повтора. SEND остаётся строкой `false`. Поддерживается literal Telegram token и
legacy Mongo `dnscluster` с существующим host/path?query и пустым connectOptions;
неподдерживаемая topology, projects, safeMode,
неизвестный ключ, отличающиеся credentials назначения или другой controller
останавливают операцию. До POST сохраняется служебный файл 0600 только с хэшами
controller/Mongo/остальных узлов, без секретов. Если POST или readback прерван,
CLI выдаёт фиксированный `cloud_configuration_apply_state_uncertain`.
Повторный `--check` подтверждает уже настроенное точное назначение и baseline
только чтением. Даже `--apply` для подтверждённого назначения не повторяет POST.
При несовпадении baseline требуется проверка текущего состояния; автоматического
повтора, удаления credentials или восстановления backup нет.
После apply проверяются неизменность остальных узлов и encrypted credential
readback, затем необходимы реальный PREVIEW/PREPARE/REPORT нового потока.
Ответ deploy не доказывает завершение запуска runtime. При неполном readback
сохранить SEND=false, проверить текущую вкладку и core backup; не переписывать
credential store и не перезапускать весь Node-RED вслепую.

Переменные окружения:

| Имя | Значение |
| --- | --- |
| TG_REACTIVATION_MANIFEST | Абсолютный путь к приватному recipients.private.json |
| TG_REACTIVATION_CONFIG | Абсолютный путь к приватной конфигурации сообщений |
| TG_REACTIVATION_MONGO_URI | URI согласованной MongoDB |
| TG_REACTIVATION_MONGO_DB | Согласованная база MongoDB |
| TG_REACTIVATION_BOT_TOKEN | Токен именно выбранного бота |
| TG_REACTIVATION_SEND_ENABLED | `true` только при разрешённом запуске |

PREVIEW читает и валидирует файлы, не подключается к Mongo и ничего не отправляет.
PREPARE создаёт `tg_reactivation_batches`, `tg_reactivation_recipients` и два
индекса, фиксирует хэши аудитории/сообщений и подтверждает полную загрузку.
Это запись в согласованную базу, выполняется только после разрешения на подключение.
Повтор PREPARE не сбрасывает результаты. Нельзя менять сообщения/аудиторию/бота
под прежним batchId после подготовки.

RUN отправляет до 25 адресатам выбранной кампании (по умолчанию academy),
START academy/friendship/group/return проходит выбранный сегмент полностью,
публикуя агрегаты после каждых 25 адресатов. START ALL последовательно проходит
friendship → group → return → academy, пропуская уже завершённые сегменты.
Он запрещён при оставшемся lock, sending или unknown в любой кампании.
Любая пауза, неопределённый результат или отсутствие прогресса останавливает
всю очередь; автоматического возобновления нет. Ручной запуск, без inject-once,
cron или автозапуска при импорте/перезапуске. Одновременно работает один
отправитель этого бота. Отключить параллельные старые рассылки: они не участвуют
в новом ограничителе. Скорость до одного запроса в 1,1 секунды; для всей базы
минимум около 4,15 часа для 13 569 адресатов плюс ответы Telegram/Mongo.

RESUME pending применяется после отдельного решения продолжить только ещё
неотправленным, оставив прежние unknown без повтора. В inject требуется
`acknowledgedUnknown` — JSON с ровно четырьмя ключами academy, friendship, group,
return и целыми неотрицательными числами из свежего REPORT. Пустой объект по
умолчанию не позволяет отправку. Карта должна точно совпадать с журналом; lock,
sending или retry_wait запрещают продолжение. Проверка повторяется перед каждым
chunk и после него для всех четырёх сегментов. Любой новый unknown или изменение
подтверждённого количества снова останавливает очередь. Прежние unknown не
изменяются и не попадают в claim. START ALL сохраняет запрет при любом unknown.
Команда ручная; автоматического продолжения после ошибки или перезапуска нет.

Для отдельно согласованной ночной паузы builders принимают sendWindow с двумя
абсолютными UTC ISO-датами stopAt/resumeAt и опциональный schedule с тем же
окном, неизменным batchId и точной картой reviewed unknown. По умолчанию эти
параметры отсутствуют, таймеров нет. При включённом окне все RUN/START/RESUME
проверяют дедлайн до claim и перед API. Во время паузы нет новых запросов,
неотправленный claim возвращается в pending без попытки. Уже начатый запрос
завершается и сохраняется; это может произойти после времени остановки.

Отдельный Function планирует ровно два UTC-таймера на сервере, не ожидает их в
OnStart и отменяет их в finalize. Утреннее возобновление допускает опоздание менее
60 секунд, проверяет прежнюю карту unknown и все прежние блокировки. Новый unknown
не подтверждается автоматически. После пропущенного времени утреннего запуска
таймер не начинает рассылку позже: требуется отдельное решение. Это расписание
не повторяется на следующий день или год.

STOP доступна во время полного прохода: завершает текущий запрос и сохраняет
результат, затем прекращает новые отправки. Для продолжения снова нажать START.
Если остановка пришла до API, подтверждённая неотправленная запись остаётся pending.

При 429 сохраняется retry_after, проход останавливается, повтор до трёх попыток
возможен после указанного срока. Ошибка текста/медиа/авторизации и неопределённый
результат останавливают проход. Не редактировать конфигурацию уже начатой кампании.

## Что измеряется

Отчёт REPORT и выход Function возвращают только агрегаты для четырёх кампаний:
eligible, attemptedRecipients, attempts, accepted, blocked, unreachable, failed,
pending, sending, retry_wait, unknown, suppressed_blocked, acceptanceRate, UTM.
Счётчики рассчитываются по сохранённым состояниям, не увеличиваются повторными
callback/нажатием кнопки. `attempts` — число начатых попыток API, в том числе повторов;
`attemptedRecipients` — уникальные адресаты с начатой попыткой.

- **accepted / отправлено**: Telegram вернул Message с message_id и нужным chat.id.
  Это подтверждение приёма сообщения Telegram, доставка/прочтение не измеряются.
- **blocked**: только 403 с точным `bot was blocked by the user`.
- **unreachable**: удалённый аккаунт, chat not found или запрет инициировать диалог.
- **unknown**: timeout, неопределённый ответ или незавершённая попытка после сбоя.
  Такие адресаты автоматически повторно не отправляются.
- **suppressed_blocked**: блокировка ранее подтверждена этим модулем для того же бота.
  Существующие исторические блокировки пока не импортируются. Разблокировка
  потребует отдельного подтверждённого входящего события и согласованной доработки.

API использует только api.telegram.org, ограничивает время/размер ответа.
В debug нет chatId, payload Telegram, токенов, URI и сырых ошибок.
В базе есть адреса доставки, поэтому доступ к коллекциям должен быть ограничен.
Поадресный журнал можно выгрузить приватно отдельно, агрегаты нельзя использовать
как доказательство индивидуальной покупки.

## Сбой и восстановление

Перед API подтверждается атомарное состояние `sending`. Если Telegram ответил,
но запись результата не подтверждена, блокировка бота сохраняется. TTL и
автоматического перехвата блокировки нет. При повторном запуске отправка запрещена.

Восстановление разрешается после остановки прежнего процесса/отправителя,
а не просто по истечении времени. Через отдельный ручной inject передать
`action: recover`, `owner` из REPORT.lock и `workerStopped: true`.
Все `sending` этого владельца переводятся в `unknown`, затем снимается блокировка.
Нельзя возвращать `unknown` в `pending`: Telegram не предоставляет идемпотентного
ключа для sendPhoto/sendVideo/sendMessage. При неопределённости возможен пропуск,
поэтому требуется приватная сверка, а не автоматический повтор.

Откат модуля: остановить отправитель, отключить вкладку, сохранить журнал.
Отправленные сообщения и уже созданные данные этим откатом не отменяются.
Не включать старый send-all inject как восстановление новой кампании.

## Покупки — следующее подключение

`purchased`, `revenueRub`, `purchaseConversion` пока **null**, не ноль.
Нужно событие подтверждённой оплаченной покупки: уникальный purchaseId,
paidAt, фактическая сумма, campaignId/utm.campaign и доказательство атрибуции.
Покупки дедуплицировать по purchaseId; считать оплаченные, отдельно учитывать
возвраты и различать количество покупок и уникальных покупателей.
Общие UTM дают атрибуцию кампании, но сами по себе не связывают покупку с chatId.
Для индивидуальной воронки нужен доверенный переход/идентификатор пользователя;
телефон, имя или похожий email не являются основанием для объединения личностей.
Промокод без меток сам по себе не доказывает источник покупки.
