# Акционные карточки sub_hab

Владелец реализации: команда LK. Аудитория: получатели акционных ссылок, в том числе Санкт-Петербург.

Поддерживаемые ссылки после публикации standalone storefront:

- `https://padlhub.ru/sub_hab?offer=friendship-promo`
- `https://padlhub.ru/sub_hab?offer=academy-promo`
- `https://padlhub.ru/sub_hab?offer=ra-promo`

`offerKey` поддерживается как прежний alias. Пустой, неизвестный, снятый с продажи
`sport-promo` или конфликтующий параметр показывает ошибку без покупки обычного тарифа.
Без этих параметров работает прежняя общая витрина. `autoPurchase` не запускает покупку.

Каждая ссылка показывает одну карточку в дизайне sub_hab, на 30 дней, без счётчиков
обычных тарифов и без годового переключателя. Цена и привязка берутся из существующего
allowlist `tournamentSubscriptionCatalog.ts`: Дружба — 4 900 ₽, Академия/РА — 11 900 ₽.
Это прежние акционные display-цены, а не live quote: перед публикацией требуется сверить
цену, доступность и ограничения точных товаров в CRM. Цена платежа принадлежит CRM;
фронтенд не передаёт сумму или процент скидки. Сам параметр offer не подтверждает
географическую/персональную eligibility; ограничения остаются у соответствующего товара.

## Покупка и возврат

После явного выбора карточки используется существующая авторизация. После входа
нужно нажать «Продолжить оплату»; автоматического create при входе, монтировании или
возврате из банка нет. Покупка идёт через существующий `apiBuySubscroption` с точным
акционным product ID и `retries: 0`. Поведение остальных callers API не меняется.

Direct CRM transaction не имеет frontend-контракта идемпотентности/подтверждения
summer operation. Поэтому новая ветка не создаёт `summerPaymentRef`, не обращается
к summer purchase/confirm и не утверждает, что оплата прошла, только на основании
возврата браузера. Return URL сохраняет offer, authMode, cabinetUrl и attribution,
добавляет `promoPaymentReturn=1`, выставляет `autoPurchase=0`.

Перед POST сохраняется локальный marker. Web Locks исключает одновременную отправку
из двух вкладок одного браузера. Ошибка, неизвестный ответ или отсутствие безопасной
HTTPS-ссылки сохраняют marker и предлагают проверить кабинет/обратиться в поддержку.
При отсутствии Web Locks или доступного localStorage покупка не отправляется.

Marker `padlhub_storefront_promo_attempt_v1:<offer>` содержит только `pending` или
`settled`, без телефона, токена и банковской ссылки. Он относится к браузеру + offer
для всех аккаунтов и намеренно не истекает, даже при подтверждённом ответе. Это также
блокирует повторное приобретение этой акции в данном браузере до ручной сверки.
Поддержка сначала устанавливает результат точной покупки в CRM/провайдере; только
после подтверждения, что новая покупка допустима, можно удалить marker данного offer
и убрать `promoPaymentReturn` из ссылки. Смена аккаунта, ошибка 4xx/5xx, ожидание или
перезагрузка сами по себе не разрешают повторный POST. Между устройствами, после
ручной очистки browser storage и со старой ab_leto2 exactly-once гарантии нет.

## Проверка и публикация

Регрессии: `node --experimental-strip-types --test scripts/tests/subscriptionStorefrontPromo.test.ts scripts/tests/subscriptionStorefront.test.ts scripts/tests/tournamentSubscriptionCatalog.test.ts`.
Эти тесты включены в существующую critical subscription CI matrix.

Сборки: `npm run build:subscription-storefront` и `npm run build:subscription-storefront:dev`.
Публикуется только отдельный storefront artifact по существующей инструкции деплоя;
Tilda-копия ab_leto2 и её редиректы не изменяются этой реализацией.

Успех локальной проверки означает карточку нужной акции, точный product ID в mocked POST,
сохранение return URL и отсутствие второго POST после неоднозначного результата.
Он не подтверждает live продажу, цену или выдачу подписки. До live-публикации нужны
CRM-сверка, проверка affected UI/API и отдельное разрешение на точный релиз.
Сигнал остановки: несоответствие товара/цены или неоднозначный результат покупки.
Метод остановки публикации: не выкладывать артефакт; после авторизованной публикации —
вернуть предыдущий standalone artifact по процедуре релиза. Это не отменяет уже созданные платежи.
