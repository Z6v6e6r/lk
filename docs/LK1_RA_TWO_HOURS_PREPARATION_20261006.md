# РА 2.0 — подготовка серверного правила

Владелец продукта создаёт отдельную подписку в VivaCRM; её ID пока не выдан.
Это разрешённая локальная подготовка серверной части, без активации продукта,
изменения существующих runtime allowlists, покупки, импорта flow или деплоя.

## Правило

`scripts/lib/lk1RaTwoHours.mjs` требует явный canonical product UUID и точное
поколение `PLAN_RULES_LIMIT_8`. Новое правило наследует обычный РА и меняет только
`productId`, `planKey: ra_two_hours`, `freeGameMinutesPerDay: 120`.

- Игра 60/90/120 минут: один визит и покрытие до 120 минут при доступном дне.
- Один общий дневной слот игры, групповой тренировки и турнира, как у РА.
  Две отдельные игры по часу не становятся двумя бесплатными посещениями.
- Лимит 8 активных записей, скидки 30/50/50 и когорта продаж сохраняются.
- Первый покрываемый групповой/турнирный формат наследуется из РА, без
  ограничения «Дружбы 2.0» направлением 5278.
- ПРО-тренировки: 50% денежная скидка без списания визита, как у РА.
- При превышении лимита активных записей бесплатные минуты/визит не выдаются.

Forward/reverse initializer проверяет точное предыдущее состояние global и
readback; запуск при пустом in-memory context разрешён для рестарта Node-RED.
Неизвестный prior не перезаписывается. Старые девять правил неизменны.

## Подготовленные исходные дельты

`buildRaTwoHoursSourceDeltas({ productId })` создаёт парные дельты:

1. `planStore`: таблицы точного продукта, дневных категорий и классификации
   имени в booking router; такие же таблицы есть в preview.
2. `freeFirst`: когорта первого события в gateway и её копия в preview.
3. `proDiscount`: allowlist ПРО-скидки из `proTrainingExclusion.mjs`, встроенный
   в gateway и preview.

Это offline helpers, не deployable flow candidate. Подмена имени сама по себе
не даёт 120 минут: policy привязана к точному продукту выбранного экземпляра.
Fixture UUID из тестов нигде не регистрируется в runtime.

## После получения ID

1. Read-only проверить новый продукт Viva: срок, визиты, направления, типы,
   клубы и допустимость игры на 120 минут должны соответствовать обещанию.
2. Зафиксировать реальный ID в том же наборе изменений и добавить интеграционные
   проверки выбранного экземпляра. Не подменять ID обычного РА.
3. Для release candidate снять свежий private live flow с `147`. Проверить
   актуальное поколение global, точные тела gateway/preview и initializer.
   При drift пересмотреть pin, не пересобирать историческим широким composer.
4. Собрать одно согласованное изменение gateway, preview и initializer,
   contract с exact preimage, графом и paired rollback. Встроенный evaluator
   уже поддерживает 120 минут; его формулу менять не требуется.
5. Отдельно подготовить статус готовности и продажу, если они входят в следующий
   разрешённый этап. Этот helper не открывает продажи и не создаёт счётчик.
6. Merge, deploy, restart, runtime global и provider write требуют авторизации
   точной операции и цели. Перед live apply сверить текущее состояние ещё раз.

Аудитория: будущие владельцы нового продукта РА 2.0. Ожидаемый результат:
игра до двух часов при неизменных остальных условиях РА. Стоп-сигнал:
несовпадение продукта, prior или исходных тел. Метод остановки: отказ генерации;
после будущей активации продажи закрываются отдельно, а уже выполненные записи
проверяются и сверяются — отключение продукта не отменяет их автоматически.

## Локальные проверки

`node --test scripts/tests/lk1RaTwoHours.test.mjs` проверяет правило, prior,
readback/откат, обратимость дельт, дневной слот и изоляцию экземпляров,
PRO allowlist, 60/90/120 минут, платное превышение, лимит 8 и паритет с РА
для неигровых событий. Тест включён в существующий exact-head CI gate.

Без ID и свежего live preimage привязка к Viva, полный live candidate,
Node-RED modular validation и реальные запись/списание пока не проверены.
