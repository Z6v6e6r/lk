# Кратко: как передать партнёру метод присоединения к существующим играм

Одна страница для владельца интеграции. Партнёрская часть — в
`partner-game-membership-integration-guide/JOIN_EXISTING_GAMES.md` (русская) и
`.../en/JOIN_EXISTING_GAMES.md` (английская).

## Что уже работает

- Метод `POST /lk/integrations/v1/open-games/{gameId}/members` **развёрнут и включён**;
  сквозной прогон на тестовой игре пройден: `201 ACTIVE`, участник в составе игры как
  `PARTNER_API`, бронь в Viva `ON_PLACE`; `DELETE` → `200 REMOVED` и отмена брони.
- Включён **один** клиент — наш канареечный `padlhub-canary`, игра — тестовая. Партёрский
  клиент не заведён.
- Комплект документов готов и лежит в репозитории (см. ниже). Приватные значения в
  репозиторий не попадают.

## Что отправить партнёру

| Файл | Зачем |
| --- | --- |
| `partner-game-membership-integration-guide/JOIN_EXISTING_GAMES.md` | сам метод: запрос, ответ, ошибки, повторы, лимиты, порядок интеграции |
| `.../ACCESS_REQUEST.md` | что нам нужно от партнёра и в каком порядке выдаём доступ |
| `.../ACCEPTANCE_TESTS.md` | приёмка перед go-live (с отметкой, что уже проверено вживую) |
| `.../SIGNING.md`, `.../ERRORS.md`, `.../IDEMPOTENCY.md`, `.../LIMITS.md` | детали подписи, кодов, повторов, лимитов |
| `.../QUICKSTART.md` + `partner-game-membership-kit/` + `.../sign.mjs` | офлайн-проверка подписи до выдачи доступов |
| `.../openapi.yaml` | машиночитаемая спецификация |
| `.../en/*` | то же на английском, если партнёру удобнее |

Приватно, вне репозитория и вне общих тикетов: точный Host/SNI, `clientId`, `audience`,
`keyId` + HMAC-секрет (base64url, ≥32 байта), клиентский mTLS-сертификат и CA, список игр
(`gameId`) со станциями и вместимостью.

## Что запросить у партнёра

**Три вещи:** исходящий IP сервера (публичный, стабильный; если плавает — CIDR и явное
предупреждение), подтверждение конкретной игры и контакт для передачи секретов (+ контакт
для инцидентов, если есть).

`clientId`, `keyId`, игру, вместимость и `audience` определяем мы. CSR не нужен: по
умолчанию сертификат и ключ выпускаем мы и отдаём готовым PKCS#12, пароль — отдельным
каналом. Если партнёр не готов передавать ключ — вариант с CSR описан в
`ACCESS_REQUEST.md` (§3).

## Порядок действий

1. Отправить партнёру комплект и запросить три пункта выше.
2. Зафиксировать `clientId`, `keyId`, игру и вместимость.
3. Выпустить сертификат и ключ (по умолчанию — мы), собрать `.p12`, сгенерировать
   HMAC-секрет; после передачи удалить у себя приватный ключ и `.p12`
   (`PARTNER_GAME_MEMBERSHIP_ACCESS_ISSUANCE.md`, §3a).
4. Добавить клиента в keyring и в `authorizedClients` анкора, добавить его сертификат и IP
   в ingress; пред-полёт гварда и рестарт (там же, §2, §4, §5, §8).
5. Передать приватные значения (`.p12`, пароль отдельно, CA, секрет, идентификаторы).
6. Партнёр проходит `ACCEPTANCE_TESTS.md` на тестовой игре; только после этого — продакшн-игра.

## Что проверить перед выдачей

- Живой прогон `POST` → `GET` → `DELETE` на тестовой игре под своим клиентом: `201`,
  `COMPLETED`, участник в составе, бронь `ON_PLACE`, затем `REMOVED`. Для этого
  канареечный mTLS-материал нужно положить на резервный хост заново (`scp`, `0600`) и
  **удалить сразу после проверки** — сейчас на хосте его нет.
- Публичные хосты без изменений: `padlhub.su` `302`, `score.padlhub.su` `410`.

## Открытый вопрос, который всплывёт первым

Партнёр спросит, **откуда брать список игр**. Сейчас игры выдаются фиксированным
allowlist, публичного метода «дай список игр» нет. Если нужен динамический выбор
(каталог, свободные места в реальном времени) — это **новый метод**, отдельная работа и
отдельное решение по контракту. В комплекте это сказано прямо, чтобы не было ожиданий.

## Чего не обещать

- PadlHub не проводит деньги: `payment` — объявление внешнего расчёта.
- Метод не создаёт игру и не меняет расписание.
- Вместимость игры ограничена: при заполнении — `409 GAME_FULL`.
- Сроки выдачи в комплекте не обещаны: они согласуются отдельно.

## Что остаётся незакрытым на нашей стороне

- Канареечный клиент всё ещё единственный `enabled`; партнёрский добавляется по шагу 4.
- Роли Mongo сервиса не сужены (`readWrite` на четырёх лишних БД) — нужно решение владельца
  и административный доступ.
- `verifyPartnerProductionIngress()` не реализован; отзыв сертификата без CRL не поддержан.
