## Подтверждённая причина для указанной игры

В production-записи четыре CONFIRMED-участника с ID. Телефоны в публичном ответе отсутствуют.
Организатор присутствует среди участников, но `metadata.organizerInMatch=false`.
`metadata.teamSlots` ссылается на участников в порядке `[0, 0, 1, 2]`:
первый игрок продублирован, четвёртый отсутствует.

Frontend удалял организатора из отображаемого состава и вариантов выбора по этому флагу,
даже если он фактически был участником. Общий обработчик выбора мог вместо изменения
расстановки результата отправлять PATCH участников, повышать игрока из листа ожидания
или менять участие организатора. После заполнения первого сета стартовая расстановка
становилась недоступной для исправления. Для фактического организатора флаг также
мог отключать ввод результата и фото, несмотря на его подтверждённое участие.

## Исправления

- Результат использует отдельный обработчик выбора: только локальный черновик,
  затем существующее автосохранение result session. Управление участием не вызывается.
- Меню использует серверный снимок result session; участвующий организатор доступен
  независимо от устаревшего UI-флага. Добавление произвольных посторонних игроков не разрешено.
- Подтверждённое участие в исходном составе включает result/фото-контролы;
  предикаты вступления, бронирования и оплаты сохранены.
- Стартовый состав доступен для исправления до отправки. Занятые позиции меняются местами.
  Исправление проходит через последующие унаследованные расстановки и останавливается
  перед первой действительно отличающейся расстановкой.
- Сервер больше не дополняет проверенную личность полями из запроса при submit,
  confirm/dispute и работе с result session.
- Чтение и запись result session привязаны к gameId; чужая сессия отклоняется до
  использования её состава и черновика.
- При миграции старого memberKey сервер повторно разрешает того же игрока по
  проверенному ID/телефону, устраняя ошибочный 403 при восстановлении.
- Регрессии result lifecycle, выбора игроков, восстановления и отправки добавлены
  в существующую обязательную CI-проверку authenticated-route security.

## Выпуск и оставшиеся ограничения

Production не исправлен до отдельного разрешения на merge и guarded release.
Исправление не записывает счёт за пользователя и не ремонтирует live-данные автоматически.
Проверка физического телефона, Safari, реального согласования другими игроками,
worker/CRM и production-сохранения результата не выполнялась.

Live session-open/query/build/update функции совпадают с базой исходников.
Live submit/confirm старее `main`: в них отсутствуют новые tenant/idempotency guards.
Нельзя импортировать целиком source-функции без проверки окружения и текущего preimage:
при подготовке live-кандидата нужно сохранить существующие guards и согласовать
совместимость с текущими runtime-зависимостями. После разрешения нужны свежий снимок,
узкий exact-graph кандидат, проверка только ожидаемых function-node изменений,
preflight/backup, readback и soak по действующему runbook.

Существующий backend submit рассчитан на четыре разных игрока (2×2).
Singles 1×1 не входил в исправление указанной doubles-игры.
Коллизия произвольного sessionId с чужой игрой отклоняется без записи чужих данных;
при Mongo duplicate-key возможна общая ошибка сохранения вместо специального сообщения.
