# Фото в чате станций ЛК1

Активный участник станции может прикрепить одно фото к сообщению, необязательно добавить подпись и открыть полученное фото внутри чата. ЛК1 подготавливает JPEG из JPG, PNG или WebP. Пределы после подготовки составляют 1600 пикселей по длинной стороне и 512 КиБ на файл. История содержит кнопку открытия, а файл загружается по нажатию.

## API и хранение

- `POST /lk/communities/:communityId/message-photos` принимает `{requestId,caption,jpeg}` с проверенным Bearer. Поле `jpeg` содержит base64 без префикса, а пустая строка в `caption` означает фото без подписи. Сервер декодирует JPEG и повторно кодирует его без метаданных. Повтор одного действия использует тот же UUID.
- Сообщение проходит через существующий владелец записи станции. Хеш запроса связывает подпись и дескриптор файла с автором и станцией. Запись в закрытом S3-префиксе `lk-station-chat/v1/` условная и привязана к ID сообщения и SHA-256. Только после подтверждения записи файла владелец принимает сообщение через прежний CAS. Mongo и outbox содержат ограниченный дескриптор, событие и текст для старых клиентов. Исходные байты и ключи доступа не входят в клиентские ответы истории.
- `GET /lk/communities/:communityId/message-photos/:messageId` проверяет подтверждённое сообщение и событие, текущую запись станции и активное членство. После чтения из S3 членство проверяется повторно. Для упорядоченного чата сообщение должно быть опубликовано в текущем потоке. Ответ содержит JPEG с заголовком `Cache-Control: private, no-store`.
- Обычный GET истории ЛК1 добавляет `photo: {hasCaption}` к соответствующим сообщениям и `stationPhotoSendEnabled: true` для участника, когда включена отправка. Текст «Фото» сохраняется для сообщения без подписи, поэтому старые клиенты отображают его как обычный текст. Форматы частной истории v2/v3 и подтверждения v1 сохраняются.
- При потере ответа повтор с прежним UUID и тем же фото возвращает исходное сообщение. Изменение фото или подписи с прежним UUID даёт конфликт. При отсутствии подтверждения из S3 сообщение остаётся скрытым. Рабочий процесс восстанавливает уже принятые сообщения с дескриптором без повторной записи файла.

## Подготовка тестового контура

1. Сверить активную схему Node-RED с исходниками владельца сообщений станции. При сборке по текущему контракту применить `patchStationMessageHistory` перед `patchStationMessageOwner` и передать владельцу `stationPhotos: true`. Компоновка требует проверенный SHA, существующие проверку пользователя и правила состава станции.
2. Зафиксировать версии кодировщика JPEG на время повторов, поскольку хеш зависит от результата перекодирования. Подготовить в окружении Node-RED проверенные версии `sharp` и `@aws-sdk/client-s3`, а также закрытый бакет с доступом на чтение и условную запись в отдельном префиксе. Настройки читаются из `LK_STATION_CHAT_PHOTO_BUCKET`, `LK_STATION_CHAT_PHOTO_REGION`, `LK_STATION_CHAT_PHOTO_ACCESS_KEY`, `LK_STATION_CHAT_PHOTO_SECRET_KEY` и при необходимости `LK_STATION_CHAT_PHOTO_ENDPOINT`. Проверить поддержку `If-None-Match: *` и проверки SHA-256 на выбранном S3-сервисе. Защитить POST на входе лимитом размера около 720 КиБ и ограничением частоты. Проверить индекс поиска сообщения по ID или по паре станция/ID.
3. Подготовить совместимые Node-RED и rating worker до первой отправки фото. При наличии потребителя уведомлений станции включить обновлённый код проверки сообщения. Установить `LK_STATION_CHAT_PHOTO_SEND_ENABLED=true` в целевом контуре после проверки записи и чтения синтетического файла. Сборка ЛК1 получает доступность из истории и не требует отдельной переменной Vite.
4. Проверить два аккаунта на одной станции, фото без подписи и с подписью, повтор после неизвестного результата и отказ чтения после удаления из станции. Проверить Chrome, выбор фото на iPhone и Android, а также сохранение старой текстовой истории.

Для остановки отправки выключить `LK_STATION_CHAT_PHOTO_SEND_ENABLED` и сохранить совместимые чтение, восстановление и S3. Объекты незавершённых попыток могут остаться после потери ответа или смены состава. Очистка возможна только после сверки с подтверждёнными сообщениями и незавершёнными запросами. Возврат старого владельца или воркера после первой записи требует отдельной проверки совместимости.
