# Subscription router background failure diagnostic

Owner: LK backend. Audience: incident triage. The existing
`subscription_router_background_failed` warning now distinguishes the internal
step and original local error without logging payloads or customer identifiers.
This change does not repair or retry a subscription/payment operation.

The warning retains `event`, `code` and numeric `statusCode` and adds:

| Field | Meaning and boundary |
| --- | --- |
| `step` | Exact static router step allowlist, otherwise `UNKNOWN` |
| `originalError` | Enum mapped from exact local error literals, otherwise `UNKNOWN` |
| `correlationHash` | `c1:` + SHA-256 of a domain-separated fresh server UUID; `null` if crypto is unavailable |
| `correlationScope` | Always `WARNING_EVENT` |

`Viva token error` maps to `VIVA_TOKEN_ERROR`, and `Failed to fetch Viva
transaction` maps to `VIVA_TRANSACTION_FETCH_FAILED`. Dynamic messages,
objects and newly introduced unlisted errors are deliberately `UNKNOWN`.
Extend the explicit mapping when adding a new local error; a regex accepting
arbitrary enum-shaped input is not an adequate privacy boundary.

The hash identifies one diagnostic occurrence. It is freshly minted for every
warning, including repeated warnings for the same operation. It does not join
retries, payment rows, provider requests or a later business outcome. `_msgid`,
incoming correlation headers, existing diagnostic contexts, payment references,
client IDs, raw errors and payloads do not enter the hash. No new secret/key or
persistent context state is required. Only the existing `global.get("crypto")`
provider is used; missing crypto produces safe enums and a null hash. There is
no `Math.random`, timestamp, identifier-hash or payload fallback.

The observer runs only in the existing background `fail(...)` branch. Crypto,
serialization or logger errors cannot change its response or output ports.
The branch still suppresses the HTTP output. `statusCode: 502` is the local
failure status; it does not establish an HTTP 502 sent to a client or the
provider's actual response. Payload/error details in existing response objects
are unchanged and are not copied into the warning.

## Source and candidate boundaries

The canonical Function source embeds the generated helper from
`scripts/lib/subscriptionRouterBackgroundDiagnostic.mjs`. The tests verify that
the embedded helper matches the module exactly.

`subscription_router_diagnostic_generation.json` records only this canonical
source successor. The newest-first registry and topology-dependent source
rejection list include it. Historical manifests and the monthly composer retain
their exact old pins; the monthly test fixture binds its reviewed historical
router and separately rejects this unbound successor.

The deployed router is longer than the canonical source. For a separately
authorized release, use `composeSubscriptionRouterDiagnosticCandidate` with a
fresh verified private external workspace's bytes and reviewed whole-flow hash.
Its default function preimage pin is the investigated source SHA256
`9be6be1d289e2b2d489776aae3b5cc6f7c6a2b00302523fa56ba3e09660c4316`.
It applies the same diagnostic splice to that exact source, preserving all other
business code. It selects the sole active router and preserves the disabled
same-name orphan. A repeated patch or source/anchor/identity drift is refused.
The exact graph contract permits only the selected node's `func` field to change.
No tracked flow JSON, import/export file, route, wiring, response node or config
node is regenerated by this PR. Existing confirm/purchase endpoints are unchanged.

Candidate composition is offline and grants no apply authority. The present
change is a Draft PR only. Before any future activation: refresh and verify the
live preimage, check the crypto provider capability, review the one-field
candidate/contract and preserve guarded recovery custody. No API, DB, provider
or queue pull/replay is needed to test this diagnostic.

Stop signal: unknown preimage/anchor, fields outside the safe schema, changed
output routing, or crypto/logger failures escaping into business handling.
Stop method: refuse candidate composition; do not import/restart. Existing
source preimage and reviewed recovery mechanisms remain the rollback boundary;
there is no added product flag or persistent diagnostic state.
