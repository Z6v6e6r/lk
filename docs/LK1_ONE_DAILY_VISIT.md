# Одно посещение абонемента в день

Решение владельца от 08.11.2026: один экземпляр абонемента может списать не более
одного посещения за московскую дату события, суммарно по всем категориям. Это
заменяет раздельный учёт первого группового события/турнира и бесплатного часа игры.
После использования дневного посещения следующая запись сохраняет существующую
скидку или клубную доплату, без второго посещения и бесплатных минут.

Реализация — focused generation `scripts/patch_live_lk1_daily_visit.mjs`, а не
пересборка устаревших исходных flow. Она изменяет только `func` четырёх узлов:

- `lk_subscription_booking_router_20260804`: общий дневной usage и атомарный guard;
- `lk_subscription_managed_policy_20260820`: запрет второго посещения;
- `lk_subscription_price_preview_20260908_router`: такой же дневной usage;
- `lk_subscription_price_preview_20260908_evaluate`: такой же запрет в preview.

Затронуты `/lk/subscription-bookings`, LK1-пути `/lk/games/split/create` и
`/lk/games/:id/split/join`, advisory `/lk/subscription-price-preview`.
Новые маршруты, конфигурация правил, credentials и схема импортов не меняются.

Guard использует встроенную уникальность Mongo `_id` в существующей коллекции
`lk_subscription_daily_booking_ops`: `lk1-daily-visit:[tenant,subscription,date]`.
Это отдельный тип документа без `actorClientId` и `lk1.rule`, поэтому он не входит
в запросы allowance-операций. Индексная миграция не требуется. Сначала сохраняется
обычная `PREPARED`-операция, затем guard; Viva write разрешён только после durable
acknowledgement или точного readback принадлежности guard этой операции.

Параллельный проигравший запрос помечает только свою ещё не начатую операцию
`FAILED / LK1_DAILY_VISIT_CHANGED` и получает 409 до создания Viva booking.
Повтор с тем же operationId заново проверяет право/usage/цену; обновление этой
операции выполняется CAS. Более дорогая запись не создаётся по старой бесплатной
котировке. Неопределённые acknowledgements и исходы провайдера остаются pending.

Guard не имеет TTL. Передача другому operationId разрешена только после доказанной
терминальной отмены `RELEASED` с привязанным bookingId/readback. Состояние `FAILED`
не разрешает передачу: прежний владелец ещё может повторить свою операцию.
Прерванный запрос после записи guard восстанавливается тем же operationId, не
создавая guard без основной операции. Отмена в Viva, ещё не согласованная с журналом
ЛК, консервативно удерживает дневное посещение; автоматический ремонт исторических
отмен и возвратов не входит в исправление.

Проверки: `node --test scripts/tests/lk1DailyVisit.test.mjs`. Матрица включает оба
порядка категорий, игры/тренировки/турниры, разные экземпляры и даты, московскую
полночь, provider-only bookings, дедупликацию, клубные ветки, гонку, потерю ack,
повтор владельца, отмену и отказ передачи по истечению времени.

Подготовка на свежем приватном snapshot (без live writes):

```sh
npm run nodered:modular:pull-147 -- /private/tmp/lk1-daily-visit-preimage
node scripts/patch_live_lk1_daily_visit.mjs /private/tmp/lk1-daily-visit-preimage
```

Патчер закрепляет SHA всего preimage и четырёх функций, проверяет exact graph
contract и сохраняет candidate/contract только в приватный внешний workspace.
При drift требуется review нового preimage. Приватные flow-файлы не публикуются.
Merge, применение candidate, restart и live postchecks требуют отдельного разрешения.
До этого прод продолжает прежнее поведение. Откат — exact guarded rollback
candidate к исходному flow; он не отменяет уже созданные bookings/списания и не
удаляет guard-документы. Перед повторным включением требуется сверить живые условия.

Владелец изменения: LK backend. Пользователи: владельцы абонементов в существующем
LK1-контуре. Сигнал остановки rollout: второе посещение за день, расхождение preview
и записи, неизвестный исход списания. Метод остановки: прекратить rollout и
использовать существующий guarded rollback по exact source/candidate contract.
