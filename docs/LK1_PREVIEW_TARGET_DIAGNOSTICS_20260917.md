## 4. Причина хронического класса (подтверждено продом)

Первый же отказ после выката (20:29 MSK) вернул:

```json
{"error":{"code":"TOURNAMENT_DISCOUNT_TARGET_UNRESOLVED","details":{"stage":"event_target",
 "observed":{"httpOk":true,"resolved":true,"idMatch":true,"category":"tournament",
 "expectedCategory":"tournament","startsAtParsed":true,"startsInPast":true,"durationMinutes":90,
 "hasRoom":true,"hasStudio":true,"externalEventTypeId":"viva:direction:5278:type:839",
 "status":null,"cancelled":false}}}}
```

То есть **единственное нарушенное условие — `startsInPast: true`**: ЛК запрашивает скидку по
подписке для турнира (и групповой тренировки), который уже начался. Всё остальное — категория,
идентичность, время, комната, студия, тип/направление — сходится. Это не порча данных и не
сбой Viva: условие `|| !Number.isFinite(start) || start <= Date.now()` в
`scripts/nodered_subscription_price_preview_nodes/router.js` (шаг `groupExercise`) переводит
известное клиенту состояние «событие уже началось» в 503, и кабинет показывает
«Не удалось проверить скидку по подписке.» вместо понятного «запись недоступна».

Класс хронический (10–22 отказа в день), а не всплеск: это взгляд пользователей на прошедшие
слоты расписания. Всплеск `PRICE_PREVIEW_GAME_UNRESOLVED` 15:04–17:16 (игровой путь, 10+ разных
клиентов) в этом окне не повторился, поэтому его подусловие (`game_record` / `game_metadata` /
`game_exercise`) ещё не наблюдено — детали появятся при повторе.

### Фикс: `lk1-event-started-unavailable`

Двенадцать условий шага `groupExercise` вынесены в именованные проверки, объединение условий не
изменилось, а здоровое во всех отношениях событие, которое уже началось, отвечает **200 без
котировок** вместо 503. Цена не публикуется, ничего не становится доступным для записи, а шлюз
записи сохраняет собственную проверку окна цели; любая другая аномалия остаётся fail-closed 503 с
`error.details`.

Почему не «200 с котировками `UNAVAILABLE`»: на этом шаге `ctx.metadata`/`ctx.catalog` ещё не
загружены, а `quote()` для событийного маршрута читает `ctx.metadata[subscriptionId]`, поэтому
честные поштучные котировки потребовали бы перестройки шага; пустой список ЛК для событийного
маршрута уже понимает (ошибки нет, скидка не предлагается).

Доказательства:

* `lk1TargetDiagnostics.test.mjs` перебирает **все 4096 комбинаций** двенадцати условий против
  ревьюенного исходника и утверждает, что решение совпадает с исходной конъюнкцией
  (`accepted` / `refused` / `client-unavailable`);
* патчер генерации `lk1-event-started-unavailable` держит 44 места отказа идентичными и пинит
  преimage `eca9e657…`, установленное тело превью `c316d6e1…` и новое тело `1bd8d443…`;
* обёртка `nodered:lk1-event-started:deploy-147` готова; **деплой не выполнялся** (нужно
  отдельное разрешение владельца: это изменение решения на платёжном пути).

Альтернатива без изменения сервера — фронтовый guard: не запрашивать скидку для события, у
которого `Date.parse(summary.timeFrom) <= Date.now()`; требует релиза фронта и правки в двух
местах (группа и турнир).

## 5. Протухшие `PAYMENT_PENDING` (2495 записей)

`lk_tournament_subscription_sales` держал 2 495 записей `PAYMENT_PENDING`, 2 304 из них с
истёкшим дедлайном; диспетчер сверки выбирает строки по `paymentPolling.nextCheckAt`, поэтому
1 640+ записей перечитывались из провайдера каждый час бесконечно (у отдельных строк 61 цикл
восстановления), не превратившись в оплаченные.

Сделано:

* `scripts/lib/subscriptionPaymentPolling.mjs` — граница `maxRecoveryChecks = 24`: архивная
  строка, достигшая границы, получает `recoveryClosedAt` / `recoveryClosedReason:
  RECOVERY_CHECK_LIMIT` и `nextCheckAt: null`; строка с `recoveryClosedAt` больше не
  диспетчеризуется и не перезаписывается. Финансовое состояние не меняется: статус продажи,
  transactionId, суммы и провайдерский дедлайн остаются, позднее подтверждение провайдера
  по-прежнему побеждает локальное закрытие, а `subscriptions:reconcile-viva` остаётся способом
  разобрать позднюю оплату.
* `scripts/close_subscription_payment_polling_backlog.mjs` — закрытие накопленного хвоста
  (по умолчанию dry-run, `--apply`, отчёт каждый запуск, compare-and-swap по прочитанному
  преimage, постчек финансового состояния).

Применено на 147 (два прохода):

```text
проход 1: selected=2295, applied=2280, conflicts=15
проход 2: selected=15,   applied=15,   conflicts=0
после:    closedForPolling=2295, schedulableInFuture=1733 -> 7,
          paidWithClosedPolling=0, paymentPending=2495 (не менялось)
```

## 7. Остаточные риски

* Подусловие всплеска `PRICE_PREVIEW_GAME_UNRESOLVED` (игровой путь) не наблюдено: всплеск не
  повторился. Диагностика включена, при повторе причина будет видна в теле ответа.
* Фикс «событие уже началось → 200 без котировок» реализован и покрыт тестами, но не
  выкачен: генерация `lk1-event-started-unavailable` собрана и проверена локально
  (кандидат `a948f18b…`), деплой требует отдельного разрешения.
* Граница `maxRecoveryChecks` не выкачена в Node-RED: хвост закрыт данными, а deployed-поллер
  продолжит планировать час вперёд только для новых архивных строк (7 строк на момент проверки).
  Выкатка генерации поллера — отдельный шаг.
* Детали отказа не содержат PII, но увеличивают тело 503; при необходимости диагностику можно
  снять следующей генерацией.
