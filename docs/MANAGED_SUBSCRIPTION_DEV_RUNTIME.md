# Managed subscription DEV runtime

## Назначение

Локальная страница ЛК `/lk_subscription_dev` позволяет проверить, как серверный
evaluator применяет конкретную DRAFT-версию правил из DEV ЦУП. Страница не
создаёт записи в Viva, не вызывает оплату, не пишет в production MongoDB и не
меняет правила в ЦУП.

Это проверка интерфейса и серверного решения `quote -> reserve -> release`, а не
доказательство интеграции с Viva. DRAFT копируется в память процесса и только
там помечается `PUBLISHED`, потому что production evaluator ожидает
опубликованный snapshot.

## Запуск

Нужен доступный DEV ЦУП и точная версия правил. Не следует оставлять выбор
версии неявным при приёмочном тесте: новый DRAFT может иметь другие опции.

```bash
MANAGED_SUBSCRIPTIONS_DEV_RUNTIME=1 \
MANAGED_SUBSCRIPTIONS_CUP_BASE_URL=http://127.0.0.1:3010 \
MANAGED_SUBSCRIPTIONS_TYPE_CODE=annual-dev-ac6396e \
MANAGED_SUBSCRIPTIONS_POLICY_VERSION=1 \
npm run dev -- --host 127.0.0.1 --port 3036
```

Открыть: `http://127.0.0.1:3036/lk_subscription_dev`.

Без `MANAGED_SUBSCRIPTIONS_DEV_RUNTIME=1` middleware не регистрируется. Маршрут
страницы также ограничен `import.meta.env.DEV` и отсутствует в production build.

## Что можно проверить

Стартовое состояние содержит две синтетические активные услуги. Все события,
станции, цены и идентификаторы выбирает сервер из закрытого тестового каталога;
браузер передаёт только `targetId`.

| Сценарий версии 1 | Ожидаемый результат |
| --- | --- |
| Создание игры 60 минут, station A, 18 августа | разрешено; услуга бесплатна, доплата станции 150 ₽ |
| Создание игры 90 минут, station A, 18 августа | разрешено; 1/4 от 4 000 ₽, скидка 20%, доплата 150 ₽, итого 950 ₽ |
| Создание игры 120 минут, домашняя станция | разрешение действия без подходящей ценовой льготы |
| Создание игры 22 августа | блок `BOOKING_WINDOW_EXCEEDED` при окне 4 дня |
| Неизвестная станция | блок `STATION_NOT_ALLOWED` |
| Групповая тренировка без включённой льготы | блок `EVENT_NOT_INCLUDED` |
| Аренда ракетки | скидка 10% и применимая станционная доплата |
| Три активные услуги | следующий резерв блокируется `ACTIVE_SERVICES_LIMIT_REACHED` |
| Освобождение резерва | активный счётчик уменьшается, доступность пересчитывается |

Кнопка «Задать состояние» позволяет установить 0–3 синтетические активные
услуги. «Обновить правила» повторно читает закреплённую версию из DEV ЦУП и
возвращает стартовые две услуги.

## DEV API

- `GET /__dev/managed-subscriptions/session` — snapshot правил, лимитов и ledger;
- `POST /quote` — проверка без резерва, body `{ "targetId": "..." }`;
- `POST /reserve` — атомарный in-process резерв с `operationId`;
- `POST /release` — освобождение тестового резерва с `operationId`;
- `POST /seed` — установка числа активных услуг;
- `POST /reset` — повторная загрузка правил и сброс состояния.

Повтор одного `operationId` с тем же payload возвращает replay, а с другим —
`IDEMPOTENCY_CONFLICT`. Mutating-запросы сериализуются одной in-process очередью,
поэтому два параллельных резерва не занимают последний слот одновременно.

## Ограничения и безопасная граница

- состояние и ledger существуют только в памяти и очищаются при перезапуске;
- тестировщик показывается маской, без исходного телефона;
- нет `clientSubscriptionId`, provider booking, денег, публикации или уведомлений;
- нет проверки реальных статусов отмены/no-show/refund — для них нужны
  подтверждённые Viva HAR-контракты и отдельный интеграционный этап;
- перенос в production требует опубликованной immutable policy, отдельной
  SubscriptionInstance, атомарного UsageLedger и server-owned mapping событий и
  станций.
