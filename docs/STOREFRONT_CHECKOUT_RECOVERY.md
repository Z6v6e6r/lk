# Storefront closed checkout recovery

The storefront resumes the saved payment directly. Cached counter responses may omit
`counterKey`; an explicit different counter is still rejected. Automatic authenticated
checkout stays headless, with notices shown by the subscription catalogue. Login and
required terms retain their dialogs. Every interrupted automatic flow releases its UI
root while retaining uncertain payment guards.

Monthly Friendship can release an old browser guard only when the backend returns an
exact operator reset receipt for that reference and transaction. A local PAID marker,
a different known transaction, or a different active shared attempt wins over reset.
The accepted receipt explicitly identifies an unpaid card payment whose Viva status is
`REJECTED` with `declineOutcome: EXPIRED`; this is distinct from an expiry command ACK.
A restored page only clears the closed attempt. A current trusted purchase gesture may
create once after rechecking the same displayed positive price. Other expired or
ambiguous operations continue to fail closed.

The November 11 bounded repair uses a frozen set of six old Friendship records and
preserves purchases created from 06:00 UTC onward. Provider transaction, client,
product, amount, payment ID, link, deadline, and absence of paid/refund facts were checked
before each conditional local update and again afterward. No generic rejected-card
reset or automatic future bulk reset is introduced. Private preimages, journal and
postchecks remain in the protected server operation workspace; no customer exports
belong in Git.

The Node-RED release patch reads a fresh full live flow, pins the exact confirm function
preimage and changes only that function body. Use the reviewed function-only deployment
contract and retained backup. Deploy backend receipt support before the storefront.
The static storefront release contains only its bundle and manifest and preserves the
main cabinet release. Do not clear local storage manually to bypass an unknown payment.
