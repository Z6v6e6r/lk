# Присоединение игрока к существующей игре

Метод-ориентированное руководство: ровно то, что нужно, чтобы добавить вашего игрока в
**уже существующую открытую игру** PadlHub. Игра создаётся организатором в ЦУП — вы её не
создаёте и не изменяете.

- **Что делает:** добавляет внешнего игрока в состав игры и создаёт бронь в Viva на нашего
  технического клиента с `paymentType=ON_PLACE`.
- **Чего не делает:** не создаёт игру, не меняет её расписание, не принимает деньги и не
  проводит платёж. Расчёт за игру происходит в вашем приложении.

Полный контракт: [ENDPOINTS.md](ENDPOINTS.md) · подпись: [SIGNING.md](SIGNING.md) ·
ошибки: [ERRORS.md](ERRORS.md) · повторы: [IDEMPOTENCY.md](IDEMPOTENCY.md) ·
лимиты: [LIMITS.md](LIMITS.md) · приёмка: [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md).

## 1. Как узнать, в какие игры можно присоединять

`gameId` берётся **из списка, который PadlHub выдаёт вместе с доступами** (`allowlist`
клиента). Публичного метода «дай список игр» в контракте нет: клиент может вызвать только
те игры, которые ему явно выданы, а любая другая даёт `403 GAME_ACCESS_DENIED`.

Практически это значит:

- вы храните выданный список игр (`gameId`) и связанные с ними данные у себя;
- связку «какая ваша игра соответствует какому `gameId`» стороны фиксируют при выдаче
  доступов;
- если понадобится динамический выбор игр (каталог, фильтры, свободные места в реальном
  времени) — это **новый метод**, а не параметр существующего; его нужно заказывать
  отдельно.

Вместе с играми выдаются: точный Host/SNI, `clientId`, `audience`, `keyId` + секрет,
mTLS-сертификат, список `stationIds` и вместимость каждой игры.

## 2. Запрос

```http
POST /lk/integrations/v1/open-games/{gameId}/members HTTP/1.1
Host: <выданный хост>
Content-Type: application/json

{ "externalPlayerId": "player-42", "displayName": "Иван П.",
  "payment": { "reference": "order-2026-000123", "paidAt": "2026-09-11T12:00:00.000Z",
               "amountMinor": 250000, "currency": "RUB" } }
```

Scope: `members:add`. Query string и фрагменты запрещены.

| Поле | Правила |
| --- | --- |
| `gameId` (в пути) | `[A-Za-z0-9][A-Za-z0-9._:-]{2,127}`, только из выданного allowlist |
| `externalPlayerId` | `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`, стабильный ID игрока на вашей стороне, не переиспользуется для другого человека |
| `displayName` | Отображаемое имя, непустая строка |
| `payment.reference` | Уникальная ссылка на внешний расчёт; в рамках клиента одноразовая |
| `payment.paidAt` | Канонический UTC ISO с миллисекундами (`new Date(x).toISOString() === x`) |
| `payment.amountMinor` | Safe integer `0 … 100000000`, минимальные единицы валюты |
| `payment.currency` | `^[A-Z]{3}$` |

`payment` **обязателен**: это объявление внешнего расчёта, а `reference` — забор
уникальности `(clientId, payment.reference)`, чтобы одна оплата не отметила двух
участников. PadlHub сумму не проверяет и денег не проводит. Схема закрытая: неизвестное
поле даёт `400 UNKNOWN_REQUEST_FIELD`.

Заголовки — восемь proof-заголовков, `Host` и `Content-Type: application/json` без
`charset`; каждый ровно один раз. Подпись HMAC v2 по каноническому JSON:
[SIGNING.md](SIGNING.md). Для `POST` нужен точный `Content-Length` в байтах UTF-8.

## 3. Ответ

Первый успех — `201`:

```json
{ "operationId": "<uuid>", "membership": { "membershipId": "<uuid>", "gameId": "<gameId>",
  "externalPlayerId": "player-42", "state": "ACTIVE", "paymentStatus": "PAID",
  "settlementSource": "EXTERNAL_PARTNER" } }
```

- `200` — идемпотентный повтор той же бизнес-команды: возвращается сохранённый результат,
  второй брони не создаётся.
- `202` — результат **неизвестен**: в теле `operation` с `state: "UNKNOWN"` и `error.code`.
  Это не ошибка; читайте операцию через `GET` — см. §6.

Сохраните `operationId` и `membershipId`: первый нужен для чтения состояния и в
обращениях в поддержку, второй — для удаления участника.

## 4. Что происходит внутри (порядок важен для понимания ошибок)

1. Проверка подписи, свежести, дублей заголовков и формата запроса.
2. Nonce-леджер: повтор перехваченного запроса отсекается здесь.
3. Идемпотентность бизнес-команды по `Idempotency-Key`.
4. Проверка доступа: клиент, scope, игра и станция из allowlist, открытость игры, наличие
   расписания и вместимости (`GAME_FULL`, `GAME_CAPACITY_*`).
5. Создание брони в Viva на технического клиента с `paymentType=ON_PLACE` и **проверка
   брони чтением** (booking + клиент + тип оплаты).
6. Запись участника в состав игры и проекции оплаты `PAID` с источником
   `EXTERNAL_PARTNER`.
7. Audit-запись операции.

Если шаг 5 не подтвердился, операция остаётся `UNKNOWN`, а участник в состав не
попадает: подтверждать то, что не проверено, система не будет.

Проверка результата на вашей стороне: участник появляется в составе игры с источником
`PARTNER_API` и связанным `vivaBookingId`, а `GET` операции возвращает `COMPLETED`.

## 5. Ошибки, которые важны именно для этого метода

| Код | Что значит | Действие |
| --- | --- | --- |
| `400 INVALID_REQUEST_BODY` / `UNKNOWN_REQUEST_FIELD` / `INVALID_*` | Тело или поле не по схеме | Исправить и отправить новую команду |
| `400 RAW_CONTENT_TYPE_INVALID` | `Content-Type` не ровно `application/json` | Исправить заголовок |
| `401 INVALID_SIGNATURE` / `INVALID_AUDIENCE` / `INVALID_TIMESTAMP` | Подпись, окружение или часы | Сверить [SIGNING.md](SIGNING.md), синхронизировать время, повторить **новой** попыткой |
| `403 GAME_ACCESS_DENIED` / `STATION_ACCESS_DENIED` / `SCOPE_DENIED` | Игра, станция или scope не выданы | Не повторять; связаться с владельцем интеграции |
| `403 MEMBERSHIP_NOT_OWNED` | Удаление чужого membership | Не повторять |
| `404 GAME_NOT_FOUND` | Игры нет | Проверить `gameId` |
| `409 MEMBER_ALREADY_ACTIVE` | Игрок уже в игре | Прочитать состояние, не создавать вторую команду |
| `409 PAYMENT_REFERENCE_ALREADY_CLAIMED` | `reference` уже использован | Не переиспользовать ссылку |
| `409 GAME_FULL` / `GAME_CAPACITY_CONFLICT` | Мест нет или гонка за место | Не повторять вслепую; показать игроку, что мест нет |
| `409 GAME_NOT_OPEN` / `GAME_SCHEDULE_UNKNOWN` | Игра закрыта или без расписания | Не повторять; проверить игру |
| `409 IDEMPOTENCY_CONFLICT` | Тот же ключ, другая команда | Остановиться и исправить команду |
| `409 REQUEST_REPLAY_DETECTED` | Переслан тот же wire-запрос | Не пересылать; новая попытка — новый proof |
| `429` | Превышен rate limit | Backoff, учитывать `Retry-After` |
| `503 VIVA_*` / `MONGO_PREREQUISITES_MISSING` / `KEY_CONFIGURATION_INVALID` | Runtime не готов | Backoff и эскалация владельцу |
| `202` | Результат неизвестен | Только `GET` операции и reconciliation |

Полная таблица со всеми кодами — [ERRORS.md](ERRORS.md).

## 6. Повторы: три разных механизма

| Механизм | Что защищает | Ключ |
| --- | --- | --- |
| Подпись + timestamp | Целостность и свежесть (±90 с) | HMAC |
| Nonce-леджер | Повтор перехваченного HTTP-запроса | `X-PadlHub-Nonce`, одноразовый |
| Idempotency-Key | Повтор бизнес-команды | `Idempotency-Key` |

1. **Не пересылайте тот же wire-запрос.** Каждая попытка — новый timestamp, nonce,
   correlation и подпись.
2. **После обрыва** (timeout, `408`, `502`, `504`) повторяйте ту же команду: тот же
   `Idempotency-Key`, то же тело, новые proof-заголовки. Ответ будет сохранённым.
3. **Новая команда — новый ключ.** Другой игрок, другая игра, другое намерение.
4. **`202` — не ошибка.** `GET /lk/integrations/v1/operations/{operationId}`, затем
   reconciliation. Слепой provider retry и автоматическая компенсация запрещены.

## 7. Лимиты

| Параметр | Значение |
| --- | --- |
| Тело | ≤ 16 384 байт; `Content-Type: application/json` без `charset` |
| Заголовки | ≤ 16 384 байт; дубли critical-заголовков и ключей JSON отклоняются |
| Запросов в секунду | 2 на клиента (burst 10), 5 на источник (burst 20) |
| Одновременных запросов | 4 на клиента, 8 на источник |
| Таймаут ответа | 15 с; TLS ≥ 1.2, mTLS обязателен |

## 8. Удаление участника

```http
DELETE /lk/integrations/v1/open-games/{gameId}/members/{membershipId}   → 200, "state": "REMOVED"
```

Тело ровно `{}` (2 байта), scope `members:remove`. Удалить можно только тот membership,
который создал тот же клиент. Бронь в Viva отменяется, участник уходит из состава игры —
это и есть корректный откат присоединения.

## 9. Порядок интеграции

1. Офлайн: сверить свою подпись с эталоном — [QUICKSTART.md](QUICKSTART.md), шаг 0
   (комплект `../partner-game-membership-kit/`, эталонная подпись
   `v2=JclK7-2hTze2KrNOPMuK0UdEO5DO2T5v6geJxxjRCAo`). Не идти дальше, пока не совпало.
2. Получить доступы и список игр ([ACCESS_REQUEST.md](ACCESS_REQUEST.md)).
3. Первый `POST` по тестовой игре; ожидать `201` и `state: ACTIVE`.
4. Реализовать хранение `Idempotency-Key` между попытками и обработку `200`/`202`.
5. Реализовать `GET` операции и ветвление по `error.code`, не по тексту.
6. Реализовать `DELETE` для отката.
7. Пройти [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md) и подписать приёмку.

## 10. Чего не делать

- не считать `payment` подтверждением оплаты на стороне PadlHub: денег мы не проводим;
- не повторять мутацию «вслепую» при обрыве;
- не выполнять компенсирующий `DELETE` или возврат автоматически;
- не логировать подпись, секрет, nonce, полное тело, `displayName`, `payment.reference`;
- не подставлять `gameId` вне выданного allowlist;
- не ожидать от метода создания игры или изменения расписания.
