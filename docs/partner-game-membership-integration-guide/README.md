# PadlHub Partner Game Membership API — руководство по интеграции

Комплект для команды партнёра (rusPadelUp): как вызывать три метода, которыми PadlHub
добавляет внешнего игрока в открытую игру и создаёт booking в Viva на нашего
технического клиента. Расчёт за игру происходит **у партнёра**, PadlHub денег не
проводит.

Англоязычная версия комплекта: [`en/`](en/README.md).

## Что можно делать уже сегодня

| Артефакт | Статус |
| --- | --- |
| Контракт (методы, подпись, ошибки, лимиты) | готов, заморожен для пилота |
| Офлайн-комплект `../partner-game-membership-kit/` (5 эталонных vectors) | готов, запускается без сети |
| Референсный подписывающий CLI `sign.mjs` (этот каталог) | готов |
| Боевой endpoint | **развёрнут и активирован**, проверен сквозным прогоном на тестовой игре |
| Ваши `clientId`, HMAC-ключ, mTLS-сертификат, тестовая игра, allowlist | **ещё не выданы** |

Боевой endpoint работает: на нашем тестовом клиенте вживую пройден полный цикл
`POST` → `GET` → `DELETE` — `201 ACTIVE`, операция `COMPLETED`, booking в Viva
`ON_PLACE`, затем `200 REMOVED` и отмена booking. Доступ партнёру при этом не выдан:
рабочий Host/SNI, `clientId`, HMAC-ключ, mTLS-сертификат и allowlist игр передаются
приватно по [ACCESS_REQUEST.md](ACCESS_REQUEST.md).

Не используйте в качестве боевого адреса ничего из этого репозитория: здесь нет
рабочих настроек. Публичный тестовый ключ из офлайн-комплекта боевым не становится.

До выдачи доступов вы можете полностью подготовить и протестировать клиент офлайн:
канонический JSON, подпись, набор headers, body и повторы проверяются комплектом
`../partner-game-membership-kit/` и `sign.mjs`.

## Модель работы

1. Клиент партнёра принимает оплату в своём приложении.
2. Клиент вызывает `POST .../open-games/{gameId}/members` и передаёт ссылку на
   внешний расчёт. PadlHub добавляет игрока в игру (ростер в ЛК/ЦУП) и создаёт booking
   в Viva на нашего технического клиента.
3. В PadlHub сохраняется проекция оплаты `PAID` с источником `EXTERNAL_PARTNER`.
   Это **заявление партнёра о внешнем расчёте**, не банковская транзакция PadlHub, не
   фискальный чек и не платёж через Viva.
4. `DELETE` удаляет только тот membership, который создал тот же integration client.
5. `GET` возвращает состояние своей операции, включая неоднозначный результат.

## Документы

Начните с [JOIN_EXISTING_GAMES.md](JOIN_EXISTING_GAMES.md) — это сам метод присоединения к
существующей игре, собранный в один документ. Дальше: [ACCESS_REQUEST.md](ACCESS_REQUEST.md),
если доступов ещё нет, и [QUICKSTART.md](QUICKSTART.md), если нужно собрать первый запрос.

- [JOIN_EXISTING_GAMES.md](JOIN_EXISTING_GAMES.md) — метод присоединения к существующей игре: запрос, ответ, ошибки, повторы, порядок интеграции.
- [ACCESS_REQUEST.md](ACCESS_REQUEST.md) — что нужно от партнёра и порядок выдачи доступов.
- [QUICKSTART.md](QUICKSTART.md) — пошаговый пример POST → GET → DELETE.
- [SIGNING.md](SIGNING.md) — канонический JSON, строка подписи, HMAC, headers.
- [ENDPOINTS.md](ENDPOINTS.md) — маршруты, тела запросов и ответов, статусы.
- [ERRORS.md](ERRORS.md) — полная таблица кодов и семантика повторов.
- [IDEMPOTENCY.md](IDEMPOTENCY.md) — повтор HTTP-запроса против повтора бизнес-команды.
- [LIMITS.md](LIMITS.md) — тело, заголовки, таймауты, rate/concurrency.
- [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md) — приёмочные тесты перед go-live.
- [ONBOARDING.md](ONBOARDING.md) — доступы, окружения, ротация, отзыв, поддержка.
- [DATA_PROTECTION.md](DATA_PROTECTION.md) — персональные данные и логирование.
- [CHANGELOG.md](CHANGELOG.md) — версии и политика совместимости.
- `sign.mjs` — референсный подписывающий CLI (Node.js 18+, без зависимостей).
- `openapi.yaml` — машиночитаемая спецификация трёх маршрутов (OpenAPI 3.1).

Полный контракт с внутренними деталями: `../PARTNER_GAME_MEMBERSHIP_API.md`
(разделы §4.1, §7, §8, §10, §11 — внутренние, для партнёра не предназначены).
Офлайн-комплект с эталонными vectors: `../partner-game-membership-kit/README.md`.
