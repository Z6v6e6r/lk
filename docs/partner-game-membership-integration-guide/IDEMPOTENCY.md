# Повторы, replay и идемпотентность

Это три разных механизма, и путать их нельзя.

| Механизм | Что защищает | Ключ |
| --- | --- | --- |
| Подпись + timestamp | Целостность и свежесть запроса | timestamp ±90 с, HMAC |
| Nonce-ledger | Повтор **перехваченного HTTP-запроса** | `X-PadlHub-Nonce`, одноразовый |
| Idempotency-Key | Повтор **бизнес-команды** | `Idempotency-Key` |

## Правило 1 — не пересылать тот же wire-запрос

Каждая HTTP-попытка обязана иметь новый `X-PadlHub-Timestamp`, новый
криптослучайный `X-PadlHub-Nonce`, новый `X-Correlation-ID` и новую подпись. Сервер
атомарно вставляет nonce в ledger; повтор того же nonce даёт
`409 REQUEST_REPLAY_DETECTED` и до игры/Viva не доходит.

## Правило 2 — повтор после обрыва

Если ответ не получен (timeout, обрыв соединения, `408`, `502`, `504`), повторите ту
же **бизнес-команду**:

- `Idempotency-Key` — **прежний**;
- method, path и тело — **прежние** (байт-в-байт канонически то же);
- `X-PadlHub-Timestamp`, `X-PadlHub-Nonce`, `X-Correlation-ID`, `X-PadlHub-Signature`
  — **новые**.

Сервер вернёт сохранённый результат без второго вызова Viva.

## Правило 3 — новый ключ для новой команды

Новая бизнес-команда (другой игрок, другая игра, другое намерение) — новый
`Idempotency-Key`. Не переиспользуйте ключ «на всякий случай».

## Правило 4 — конфликт

Тот же `Idempotency-Key` с другим method/path/body даёт `409 IDEMPOTENCY_CONFLICT`.
Это ошибка клиента: остановитесь и исправьте команду, а не подменяйте ключ случайным.

## Пример: обрыв после отправки

```text
1. POST /lk/integrations/v1/open-games/game-001/members
   Idempotency-Key: 11111111-1111-4111-8111-111111111111
   timestamp T1, nonce N1, correlation C1, signature S1
   -> соединение оборвалось, ответа нет

2. Повтор той же команды:
   Idempotency-Key: 11111111-1111-4111-8111-111111111111   (прежний)
   body: тот же
   timestamp T2, nonce N2, correlation C2, signature S2      (новые)
   -> 200 с прежним operationId и membership; второго booking в Viva нет

3. Если пришло 202 -> GET /lk/integrations/v1/operations/{operationId}
```

## Параллельные попытки

Если вторая попытка приходит, пока первая ещё выполняется, сервер не запускает
вторую операцию: вернётся `202` с текущим состоянием. Читайте операцию, не
форсируйте результат.

## `202` и `UNKNOWN`

`202` означает, что результат неизвестен (timeout, неоднозначный ACK, несовпадение
read-back). Что делать:

1. `GET /lk/integrations/v1/operations/{operationId}`;
2. если состояние `COMPLETED` — использовать его;
3. если `UNKNOWN` — передать в reconciliation на стороне PadlHub;
4. **не** выполнять слепой provider retry, `DELETE` или возврат денег.

## Сроки

- Окно timestamp — ±90 секунд.
- Nonce хранится в ledger 86 400 секунд; переиспользовать nonce нельзя даже после
  истечения окна timestamp.
- `Idempotency-Key` хранится вместе с операцией; результат реплея доступен, пока
  хранится операция.

Все значения закреплены в [SIGNING.md](SIGNING.md). Офлайн-комплект проверяет
инварианты повтора на фиксированном vector `POST_RETRY`.
