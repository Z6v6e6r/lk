# Подключение: доступы, окружения, ротация, поддержка

Конкретный список данных, которые нужны от вас, и порядок выдачи — в
[ACCESS_REQUEST.md](ACCESS_REQUEST.md). Проверка перед go-live — в
[ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md).

## Что выдаёт PadlHub

Индивидуально, приватно, отдельно для каждого окружения:

| Артефакт | Назначение |
| --- | --- |
| Base URL и точный Host/SNI | Рабочий адрес API |
| `clientId` | Идентификатор M2M-клиента |
| `audience` | Точная строка окружения (участвует в подписи) |
| `keyId` + секрет | Ключ HMAC (base64url, ≥32 байта) |
| CA + PKCS#12 с клиентским сертификатом и ключом | Транспортная идентичность; пароль от PKCS#12 идёт отдельным каналом |
| Allowlist | Разрешённые `stationIds` и игры с вместимостью |
| Scopes | `members:add`, `members:remove`, `operations:read` |

Анкета и формальное согласование контракта не требуются: PadlHub предоставляет
методы и фиксированный контракт, клиент реализуете вы. Публичный тестовый ключ из
офлайн-комплекта боевым не становится.

## Окружения

- Test и production получают **разные** `clientId`, `audience`, HMAC-ключ и
  mTLS-сертификат. Переиспользование между окружениями запрещено.
- `X-PadlHub-Audience` входит в HMAC: запрос, перехваченный в test, не будет принят
  production даже при случайном совпадении client ID.
- Клиент должен явно хранить конфигурацию окружения, а не «переключать флаг».

## mTLS-сертификат

По умолчанию сертификат выпускает PadlHub:

1. мы генерируем пару «приватный ключ + сертификат» и подписываем её нашим CA;
2. вы получаете готовый PKCS#12, пароль от него приходит отдельным каналом;
3. сертификат привязан к конкретному окружению и клиенту;
4. устанавливается на каждый исходящий запрос: mTLS обязателен и **не заменяется** ни
   CIDR, ни подписью.

Если приватный ключ не должен покидать вашу инфраструктуру — пришлите CSR, и мы вернём
подписанный сертификат. Требования и команды — в
[ACCESS_REQUEST.md](ACCESS_REQUEST.md), раздел 3.

```sh
# превратить PKCS#12 в PEM-пару для curl и большинства HTTP-клиентов
openssl pkcs12 -in client.p12 -clcerts -nokeys -out client.crt
openssl pkcs12 -in client.p12 -nocerts -nodes -out client.key
chmod 600 client.crt client.key
```

CIDR используется только как дополнительное ограничение, а не как самостоятельная
идентичность.

## Ротация ключа

Ротация без разрыва:

1. PadlHub добавляет новый `keyId` рядом со старым;
2. вы переводите клиент на новый `keyId`;
3. после согласованного grace-периода старый ключ отключается, затем удаляется.

Ваш клиент должен уметь принимать новый `keyId` из конфигурации, не из кода.

## Отзыв доступа

При инциденте PadlHub отключает client или конкретный key на ingress. Клиент увидит
`403 CLIENT_DISABLED` / `SCOPE_DENIED` или `401 INVALID_SIGNATURE`. По этим кодам
нужно **остановить мутации** и связаться с владельцем интеграции, а не ретраить.

## Чек-лист перед go-live

- [ ] Свой подписывающий код совпадает с референсным на офлайн-vectors.
- [ ] Секреты и приватные ключи лежат в защищённом хранилище, не в системе контроля
      версий и не в логах; test/prod разделены.
- [ ] `Idempotency-Key` сохраняется между попытками одной команды.
- [ ] Обработаны `202`, `409`, `429`, `408/502/504` по [ERRORS.md](ERRORS.md) и
      [IDEMPOTENCY.md](IDEMPOTENCY.md).
- [ ] Логи не содержат подпись, секрет, nonce, тело, `displayName`,
      `payment.reference`.
- [ ] Backoff учитывает rate limit из [LIMITS.md](LIMITS.md).
- [ ] Определено поведение при отзыве доступа.

## Что не нужно присылать

Дампы запросов с секретами, приватные ключи, сертификаты в открытом канале, реальные
персональные данные тестовых игроков. Для проверки подписи достаточно публичных
vectors.

## Поддержка

Точка контакта и канал эскалации передаются владельцем интеграции на стороне PadlHub
вместе с доступами; в этом комплекте контакт намеренно не публикуется. При инциденте
приложите `operationId`, `correlationId`, время в UTC, HTTP-статус и код ошибки — без
секретов и персональных данных.
