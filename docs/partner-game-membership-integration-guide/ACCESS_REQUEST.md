# Заявка на доступ: что нужно от вас

Документ описывает ровно те данные и артефакты, без которых PadlHub не может выдать
рабочий доступ. Анкета и формальное согласование контракта не требуются: контракт
фиксирован этим комплектом, клиент реализуете вы.

Передавайте значения согласованным приватным каналом. Секреты и приватные ключи в
открытый канал, тикет или почту не попадают.

## 1. Контакты

| Поле | Обязательно | Комментарий |
| --- | --- | --- |
| Организация и продукт | да | Кто именно интегрируется |
| Технический контакт | да | Инженер, который ведёт интеграцию |
| Контакт для инцидентов | да | Круглосуточно или с окном дежурства |
| Контакт по персональным данным | да | Для вопросов по [DATA_PROTECTION.md](DATA_PROTECTION.md) |
| Язык переписки | нет | Русский по умолчанию |

## 2. Окружения

| Поле | Обязательно | Комментарий |
| --- | --- | --- |
| Нужны test и production? | да | Могут быть выданы оба или сначала только test |
| Планируемая дата запуска | нет | Для порядка выдачи |
| Ожидаемая нагрузка | да | Средние и пиковые запросы в секунду, суточный объём |
| Ожидаемое число игр и участников | да | Для проверки вместимости |

Test и production получают **разные** `clientId`, `audience`, HMAC-ключ и
mTLS-сертификат. Переиспользование между окружениями запрещено.

## 3. mTLS-сертификат

| Поле | Обязательно | Комментарий |
| --- | --- | --- |
| CSR (PEM) | да | По одному на окружение |
| Алгоритм ключа | да | RSA ≥ 3072 или ECDSA P-256 / P-384 |
| SAN | нет | CN достаточно; идентичность задаёт подписант |
| Срок действия | нет | По умолчанию 12 месяцев |

Приватный ключ генерируете вы, и он остаётся у вас; нам передаётся только CSR.
PadlHub подписывает его своим CA и возвращает сертификат вместе с CA. Вы ставите
клиентский сертификат на каждый исходящий запрос: mTLS обязателен и **не заменяется**
ни CIDR, ни подписью.

## 4. Сетевые адреса

| Поле | Обязательно | Комментарий |
| --- | --- | --- |
| Исходящие IP / CIDR | да | По одному на окружение, стабильные |
| Наличие NAT с меняющимся адресом | да | Если адрес плавает — скажите, это меняет allowlist |

CIDR на ingress — **дополнительное** ограничение, а не идентичность. Если у вас нет
статического адреса, скажите об этом: ограничение по источнику согласуется отдельно,
вместо него нельзя подставлять ничего другого.

## 5. Игры и станции

| Поле | Обязательно | Комментарий |
| --- | --- | --- |
| `gameId` | да | Канонический ID игры, не Mongo `_id` |
| `stationId` | да | Станция, к которой относится игра |
| Вместимость | да | Сколько участников игра принимает — этот лимит выделяется вам |
| Приватность игры | да | Публичная или приватная |

Клиент может вызывать **только** то, что явно выдано в allowlist. Игра вне
allowlist даёт `403 GAME_ACCESS_DENIED`, станция — `403 STATION_ACCESS_DENIED`.

## 6. Идентификатор клиента и ключ

| Поле | Обязательно | Комментарий |
| --- | --- | --- |
| Желаемый `clientId` | нет | Формат `^[a-z0-9][a-z0-9_-]{2,63}$`; PadlHub подтверждает или предлагает свой |
| Желаемый `keyId` | нет | Формат `^[A-Za-z0-9][A-Za-z0-9._:-]{2,127}$` |
| Канал передачи секрета | да | SOPS/age или SSH с закреплённым host key |

HMAC-секрет передаётся как строка **base64url**, минимум 32 байта после декодирования.
Секрет не попадает ни в запрос, ни в логи, ни в этот комплект.

## 7. Чего присылать не нужно

- приватные ключи и готовые секреты в открытом канале;
- дампы запросов с подписью, секретом или nonce;
- реальные персональные данные тестовых игроков;
- переписку с боевыми `clientId` и ключами в общих трекерах.

Для проверки подписи достаточно публичных vectors из
[`../partner-game-membership-kit/`](../partner-game-membership-kit/README.md).

## Порядок выдачи

| Шаг | Кто | Результат |
| --- | --- | --- |
| 1 | Вы | Присылаете данные разделов 1–6 |
| 2 | PadlHub | Фиксирует `clientId`, `keyId`, allowlist игр/станций и вместимость |
| 3 | Вы | Генерируете ключ и CSR, передаёте CSR |
| 4 | PadlHub | Подписывает сертификат, выдаёт CA, Host/SNI, `audience`, HMAC-секрет |
| 5 | Вы | Проходите [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md) на тестовом контуре |
| 6 | Обе стороны | Подписывают чек-лист go-live из [ONBOARDING.md](ONBOARDING.md) |
| 7 | PadlHub | Включает клиента в production allowlist |

Сроки каждого шага согласуются отдельно; комплект не содержит обещаний по срокам.
До шага 4 рабочий адрес, `audience` и ключ вам не передаются.
