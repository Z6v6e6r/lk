# Access request: what we need from the partner

This document lists exactly the data and artifacts without which PadlHub cannot issue
working access. No questionnaire and no formal contract negotiation are required: the
contract is fixed by this package and the partner implements the client.

Send values over the agreed private channel. Secrets and private keys never go to an open
channel, ticket or mailbox.

## 1. Contacts

| Field | Required | Notes |
| --- | --- | --- |
| Organisation and product | yes | Who is integrating |
| Technical contact | yes | The engineer running the integration |
| Incident contact | yes | 24/7 or with a duty window |
| Data-protection contact | yes | For personal-data questions |
| Correspondence language | no | Russian by default; an English edition exists |

## 2. Environments

| Field | Required | Notes |
| --- | --- | --- |
| Test and production, or test first? | yes | Both may be issued, or test first |
| Planned launch date | no | Used for issuance ordering |
| Expected load | yes | Average and peak requests per second, daily volume |
| Expected games and participants | yes | To validate capacity |

Test and production receive **different** `clientId`, `audience`, HMAC key and mTLS
certificate. Reuse between environments is forbidden.

## 3. mTLS certificate

| Field | Required | Notes |
| --- | --- | --- |
| CSR (PEM) | yes | One per environment |
| Key algorithm | yes | RSA ≥ 3072 or ECDSA P-256 / P-384 |
| SAN | no | CN is sufficient; the signer establishes identity |
| Validity | no | 12 months by default |

The private key is generated by and stays with the partner; only the CSR is sent to us.
PadlHub signs it with our CA and returns the certificate together with the CA. The partner
attaches the client certificate to every outbound request: mTLS is mandatory and is
**not** replaced by CIDR or by the signature.

## 4. Network addresses

| Field | Required | Notes |
| --- | --- | --- |
| Outbound IPs / CIDRs | yes | One set per environment, stable |
| NAT with a changing address | yes | Say so if the address floats; it changes the allowlist approach |

CIDR at the ingress is an **additional** restriction, not an identity. If you have no
static address, tell us: the source restriction is agreed separately and nothing else may
be substituted for it.

## 5. Games and stations

| Field | Required | Notes |
| --- | --- | --- |
| `gameId` | yes | Canonical game ID, not a Mongo `_id` |
| `stationId` | yes | Station the game belongs to |
| Capacity | yes | How many participants the game accepts from the partner |
| Game privacy | yes | Public or private |

A client can call **only** what is explicitly granted in its allowlist. A game outside it
yields `403 GAME_ACCESS_DENIED`, a station yields `403 STATION_ACCESS_DENIED`.

## 6. Client identifier and key

| Field | Required | Notes |
| --- | --- | --- |
| Desired `clientId` | no | Format `^[a-z0-9][a-z0-9_-]{2,63}$`; PadlHub confirms or proposes one |
| Desired `keyId` | no | Format `^[A-Za-z0-9][A-Za-z0-9._:-]{2,127}$` |
| Secret delivery channel | yes | SOPS/age or SSH with a pinned host key |

The HMAC secret is delivered as a **base64url** string, at least 32 bytes once decoded. It
never appears in a request, in logs, in the repository or in this package.

## 7. What not to send

- private keys or ready secrets over an open channel;
- request dumps carrying a signature, secret or nonce;
- real personal data of test players;
- production `clientId`s and keys in shared trackers.

Public vectors from [`../../partner-game-membership-kit/`](../../partner-game-membership-kit/README.md)
are sufficient to verify a signature.

## Issuance order

| Step | Who | Result |
| --- | --- | --- |
| 1 | Partner | Sends the data from sections 1–6 |
| 2 | PadlHub | Fixes `clientId`, `keyId`, game/station allowlist and capacity |
| 3 | Partner | Generates the key and CSR, sends the CSR |
| 4 | PadlHub | Signs the certificate, issues CA, Host/SNI, `audience`, HMAC secret |
| 5 | Partner | Passes [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md) on the test environment |
| 6 | Both | Sign the go-live checklist in [ONBOARDING.md](ONBOARDING.md) |
| 7 | PadlHub | Enables the client in the production allowlist |

Timings for each step are agreed separately; this package makes no timing commitments.
Until step 4 the working address, `audience` and key are not handed to the partner.
